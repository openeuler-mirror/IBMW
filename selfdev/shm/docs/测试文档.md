# ibmw_shm 零拷贝共享内存 — 测试文档

> 适用代码：`selfdev/shm`（自研 iceoryx 替代件）与 IBMW 传输扩展 `src/extensions/transport/shm_ext`（§6）
> 维护约定：新增/修改用例时同步更新本文档的用例表（用例 ID 写在测试代码注释中，如 `// PS-04`）。
> CI 与其他助手只需要阅读本文件 + `scripts/run_shm_tests.sh`（核心库）/ `scripts/run_shm_ext_tests.sh`（IBMW 扩展）。

## 1. 快速使用

```bash
# 在仓库根目录（或任意目录）执行；默认只跑 unit
selfdev/shm/scripts/run_shm_tests.sh                 # Release 构建 + 全部用例 1 次
selfdev/shm/scripts/run_shm_tests.sh all             # unit debug asan ubsan tsan repeat bench
selfdev/shm/scripts/run_shm_tests.sh asan tsan       # 任意阶段组合
REPEAT=100 selfdev/shm/scripts/run_shm_tests.sh stress   # 并发/跨进程用例重复 100 次
selfdev/shm/scripts/run_shm_gen_smoke.sh             # ibmw_gen 生成 + 构建 + 运行冒烟（需 ROS 2，见 §6.1）
selfdev/shm/scripts/run_shm_switch_check.sh          # 构建开关：只开 shm 的基准、与 iceoryx 共存、shm 预设（见 §6.10）
```

使用、开关与从 iceoryx 迁移见 [使用与迁移.md](使用与迁移.md)。

| 阶段 | 内容 | 判定 |
|---|---|---|
| unit | Release 构建，全部用例 1 次 | gtest 全通过 |
| debug | Debug 构建（含 assert），全部用例 1 次 | gtest 全通过 |
| asan | AddressSanitizer + LeakSanitizer | 全通过且日志无 Sanitizer 报告 |
| ubsan | UBSan，`-fno-sanitize-recover=all` | 全通过且无 `runtime error:` |
| tsan | ThreadSanitizer | 全通过且无 `WARNING: ThreadSanitizer` |
| repeat | Release，`--gtest_repeat=$REPEAT --gtest_shuffle`（默认 20） | 每轮全通过 |
| stress | 只跑并发/跨进程/lossless 用例 `$REPEAT` 次 | 每轮全通过 |
| bench | `ibmw_shm_bench` 时延/吞吐/空闲 CPU | 不判定，报告存 `bench.txt` |

环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `BUILD_ROOT` | `<repo>/build-selfdev-shm` | 每个阶段一个子目录（release/debug/asan/ubsan/tsan） |
| `OUT_DIR` | `$BUILD_ROOT/reports` | `<stage>.xml`（JUnit）、`<stage>.test.log`、构建日志 |
| `GTEST_SRC` | 自动探测 `../deps/googletest-src` 等 | 离线 googletest 源码；为空则按 `cmake/GetGTest.cmake` 下载 |
| `REPEAT` | 20 | repeat/stress 次数 |
| `TEST_TIMEOUT` | 1800 | 单阶段测试超时（秒），超时即失败（防挂死） |
| `GTEST_FILTER` | `*` | 只跑部分用例 |
| `JOBS` | `nproc` | 构建并行度 |
| `TSAN_CC` / `TSAN_CXX` | 自动选 gcc/g++ 14→13→12 | tsan 阶段编译器，见下 |

TSan 工具链：GCC 11 的 libtsan 不拦截 `pthread_cond_clockwait`（libstdc++ 的 `condition_variable::wait_until(steady_clock)` 使用），会产生虚假的 "double lock"/数据竞争报告；脚本自动选用 GCC 12+，并加 `-Wno-error=tsan`（GCC 12 对 `atomic_thread_fence` 的 -Wtsan 提示；该栅栏只用于 futex 睡眠/唤醒声明的排序）。

退出码：全部阶段通过返回 0，否则 1；未知阶段 64。CI 接入只需：

```yaml
- run: selfdev/shm/scripts/run_shm_tests.sh unit asan ubsan tsan repeat
- artifacts: build-selfdev-shm/reports/*.xml
```

手工构建（不经脚本）：

```bash
cmake -S selfdev -B build-selfdev -DIBMW_BUILD_TESTS=ON -Dgoogletest_LOCAL_SOURCE=<googletest-src>
cmake --build build-selfdev -j
ctest --test-dir build-selfdev --output-on-failure        # 或直接运行 shm/ibmw_selfdev_shm_test
```

## 2. 测试结构

| 文件 | 套件 | 覆盖 |

| `test/pubsub_test.cc` | ShmPubSubTest | 发现、loan 上限、对齐、尺寸分级/预算、预分配池、1:N、N:M、回收复用、held 上限、新段宣告、多线程 |
| `test/policy_test.cc` | ShmPolicyTest | DISCARD_OLDEST、lossless（WAIT_FOR_CONSUMER+BLOCK_PRODUCER）、阻塞超时、多生产者阻塞 |
| `test/listener_test.cc` | ShmListenerTest | 回调、边沿触发、同步 Detach、容量、进程内 64 个上限、丢唤醒压力、空闲零唤醒 |

| `test/regression_test.cc` | ShmRegressionTest | 首轮独立代码评审发现问题的回归（RG-xx，编号对应评审条目）；含原始协议恶意发布者 RawPublisher |

| `test/test_util.{h,cc}` | — | 每个测试进程私有 `IBMW_SHM_ROOT`（mkdtemp，结束删除）、子进程管理、线程上下文切换计数 |

隔离：每个测试二进制使用私有服务目录，测试内 URL 唯一，可与其他进程/CI 作业并行运行；子进程通过环境变量继承同一目录。

## 3. 用例清单

### 3.1 平台层（PL）

| ID | 用例 | 预期 |
|---|---|---|
| PL-01 | 数据段封印 | 对端可写映射被拒（F_SEAL_FUTURE_WRITE），只读映射可见发布方写入；扩缩容被拒 |
| PL-02 | 控制段不封印 | 对端可写映射可用，双向可见 |
| PL-03 | 映射尺寸校验 | 尺寸与 fstat 不符/0/非法 fd 被拒 |
| PL-04 | futex 超时 | 超时返回 false；期望值不符立即返回 |
| PL-05 | 跨映射 futex 唤醒 | 同一 memfd 两个不同虚拟地址间 wait/wake 生效（模拟跨进程，非 PRIVATE） |
| PL-06 | fd 传递与凭据 | SEQPACKET 携带 fd；空 socket 返回 -1/EAGAIN；SO_PEERCRED pid/uid 正确；对端关闭读到 0 |
| PL-07 | 句柄编解码 | 段 12bit / 索引 20bit / 代数 32bit 往返一致 |
| PL-08 | 共享布局 | ChunkHeader 64B、back_offset@60、NotifySlot 64B、环索引 cache line 隔离、原子类型无锁 |
| PL-09 | Result/错误名 | 全部错误码有名字 |
| PL-10 | URL 哈希稳定 | FNV-1a 标准向量（socket 命名跨版本兼容） |
| PL-11 | 第三轮评审 M5、第四轮评审：接收的段必须是 tmpfs | 普通 memfd 接受；已封印的 hugetlbfs memfd（2MB）返回 `kCorrupted`（修复前为 mmap ENOMEM 的 `kNoMemory`，在有大页的系统上则被接受）。文件系统检查单独覆盖：`/proc/self/exe`（磁盘上尺寸正确的普通文件，测试根目录本身可能就是 tmpfs，所以不用它）返回 `kCorrupted`（其文件系统 magic 记录为属性 `exe_fs_magic`，若恰为 tmpfs 则跳过该断言），procfs 文件被拒；tmpfs 上的普通文件与未封印 memfd 通过文件系统检查、因缺 `F_SEAL_SHRINK` 被拒（`kCorrupted`）。是否有 hugetlb 记录为属性 `hugetlb_memfd` |
| PL-12 | 第三轮评审 H1/M6：发送队列 | socket 满时排队（`kQueued`），Flush 按序发出且排在已发消息之后，不丢不乱；随消息传递的自有 fd 发出后关闭；上限 `kMaxMessages`（4160）后 `kOverflow`；对端关闭为 `kFailed` |
| PL-13 | 第三轮评审 H1：对端死亡判定 | 存活：`PidGone`=0、pidfd 不可读；SIGKILL 后未回收（僵尸）：pidfd 可读、`PidGone` 仍为 0；回收后 `PidGone`=1；第四轮评审 L-8：只有 ESRCH 算消亡，init（pid 1）永不为 1，非 root 时 EPERM 得 -1（无法判定），`fault::kill_eperm` 同样得 -1；`fault::no_pidfd` 时 `PidfdOpen` 返回 -1/ENOSYS。是否有 pidfd 记录为属性 `pidfd` |
| PL-14 | HAP 内 fstat 被拒（§6.8）：大小改由 lseek 检查 | `fault::fstat_denied` 时：宣称 4097 字节、0 字节均为 `kCorrupted`；文件偏移移到 100 后按 4096、2048 映射成功；管道被拒（覆盖性：由 fstatfs 拒绝，未到回退分支） |

### 3.2 发布/订阅（PS）

| ID | 用例 | 预期 |
|---|---|---|
| PS-01 | 服务目录 | `<root>/ibmw_shm.<uid>.<domain>`，权限 0700 |
| PS-02 | socket 生命周期 | publisher 创建 1 个 `.sock`，析构删除 |
| PS-03 | 非法 URL | 空/超长 URL 构造失败 `kInvalidArg`；无效对象操作返回错误不崩溃 |
| PS-04 | 单消息端到端 | 内容一致；订阅方地址不同（同一 memfd 另一映射）；ChunkView 元数据；统计 |
| PS-05 | loan 上限 | 第 9 个 loan 返回 `kTooManyLoans`（与 iceoryx 8 一致）；Release/Publish 归还额度；外来指针被忽略 |
| PS-06 | 对齐 | 1~4096 对齐生效（发布与订阅两侧）；0/3/8192 被拒 |
| PS-07 | 尺寸分级与预算 | 1B~2MB 可 loan 且整段可写；>256MB 拒绝；超预算 `kNoMemory` 且 `pool_exhausted`+1 |
| PS-08 | 预分配池 | 构造时建段；稳态发布不再增长 |
| PS-09 | 1:N | 4 个订阅者均按序收到全部 32 条 |
| PS-10 | N:M | 2×2 全连接，每个订阅者收到两个发布者全部消息 |
| PS-11 | 发现顺序/隔离 | 先订阅后发布、先发布后订阅都能连上；不同 URL 不串 |
| PS-12 | 回收复用 | 稳态逐条发布并等待取走（确定性）：每条内容正确，段数 ≤4、无坏归还、无驱逐，收到 = 投递 |
| PS-13 | held 上限 | 超过 max_held 返回 `kTooManyHeld`，释放后恢复 |
| PS-14 | 持有块比发布者活得久 | 发布者析构后已 take 的块仍可读，Release 后连接移除 |
| PS-15 | 新段宣告（ACK 放行） | 每次发布都触发新尺寸级别建段，订阅方按序收到且内容正确 |
| PS-16 | 多线程并发 | 4 生产线程 ×25k + 2 消费线程；无损坏、无坏归还、两端无损坏连接；等待账目收敛后 取走 + 驱逐 = 投递（TSAN 目标） |
| PS-17 | 热块复用 | loan→发布→取走→释放 循环 100 次，每次 loan 得到同一块（Loan 先回收归还环，再从 LIFO 空闲表取块）；订阅者持有中的块不被借出 |

### 3.5 健壮性与多进程（RB）

| ID | 用例 | 预期 |
|---|---|---|
| RB-01 | ABI 不符 | 收到 Reject(kAbiMismatch) 后断开；发布者继续服务正常订阅者 |
| RB-02 | 畸形握手 | URL 不符 Reject(kInvalidArg)；垃圾报文/越序 ConnAck 直接断开 |
| RB-03 | 伪造/重复归还 | 4 种坏句柄计入 `bad_returns` 被忽略，真句柄只回收一次；池不增长 |
| RB-04 | 读索引越界 | 判定连接损坏、断开并回收；正常订阅者不受影响 |
| RB-05 | 回收环索引越界 | 判定损坏；已投递块全部回收 |
| RB-06 | 订阅方写 payload | 进程因 SIGSEGV 终止（数据段只读映射） |
| RB-07 | 残留 socket | ECONNREFUSED 的残留文件被下一个订阅者删除，活的保留 |
| RB-08 | 跨进程（父发子收） | 子进程 lossless 按序收全 5000×4KB 并校验内容 |
| RB-09 | 跨进程（子发父收）+ Listener | 2 万 ×1KB 经共享 futex 唤醒全部收到、按序 |
| RB-10 | 订阅者 kill -9 | 挂断时 10 块先隔离，确认进程已死（pidfd/kill）后全部回收；池恢复可用、不增长 |
| RB-11 | 发布者 kill -9 | 订阅者断开连接；已持有块仍可读；残留 socket 被下一个订阅者清理 |
| RB-12 | 域隔离 | 不同 `IBMW_SHM_DOMAIN` 互不发现 |
| RB-13 | 第三轮评审 H1：订阅者发未知类型消息 | 计入 `unknown_messages`，连接保留，之后的归还与投递正常（修复前断开连接） |
| RB-14 | 第三轮评审 H1：连接异常断开但订阅者仍持有块 | 原始订阅者持有 1 块后只关闭 socket（未置 closed）：该块进入隔离（`quarantined`=1、`quarantined_chunks`=1、`reclaimed`=0），此后 300 轮借满其余全部块并写入，被持有块内容始终不变；再借第 8 块时池增长而不复用它。同进程对端无法判死：`unverifiable_peers`=1。**修复前失败**：断开即回收，被持有块在后续 Loan 中被改写 |
| RB-15 | 第三轮评审 H1：有序关闭立即回收 | 真实 Subscriber 析构（持有 1 块）与原始订阅者先置 `closed` 再断开，均立即回收（`reclaimed` 1→2），不隔离 |
| RB-16 | 第三轮评审 H1：隔离直到对端进程消亡（pidfd） | 子进程（`sub_hold_drop`）持有 5 块后关掉控制 socket 并存活：5 块隔离，50 轮借用不触及；SIGKILL + 回收后 5 块回到池中（`reclaimed`=5、`quarantined_chunks`=0），借满 8 块不增长 |
| RB-17 | 同 RB-16，无 pidfd | `fault::no_pidfd` 模拟沙箱/旧内核，改用 `kill(pid,0)` 轮询（10ms 起倍增，上限 1s），结果同 RB-16 |
| RB-18 | 第四轮评审：发送队列溢出端到端 | 原始订阅者持有 1 块后停止读控制 socket；`fault::send_queue_limit`=1 + `send_would_block` 让两个新尺寸类的 SegmentAdd 溢出：`send_queue_overflows`=1、连接断开、该块隔离（`quarantined_chunks`=1、`reclaimed`=0），此后 98 次借用写入不改写它；对端随后置 `closed` 即回收 |
| RB-19 | 第四轮评审：pidfd 监视下的迟到有序关闭 | 子进程（`sub_hold_drop_release`）持有 3 块后断开并存活（有 pidfd 时本进程多 1 个 `anon_inode:[pidfd]`）；SIGUSR1 后子进程 Release 全部样本（置 `closed`）：3 块回收，pidfd 关闭（Reap → Post → PeerExited），子进程仍存活。是否有 pidfd 记录为属性 `pidfd_watch` |
| RB-20 | 第四轮评审 L-8：kill 被拒 | `no_pidfd` + `kill_eperm`：`unverifiable_peers`=1，停止轮询；子进程被杀、故障撤除后 200ms 内块仍隔离（不再查询）。**修复前失败**：EPERM 当"存活"无限轮询，`unverifiable_peers`=0 |
| RB-21 | 第四轮评审：关闭死亡判定 | `PublisherOptions::peer_death_check=false`：不打开 pidfd、`unverifiable_peers`=1，子进程死后块仍隔离，只有有序关闭或发布者析构释放 |

### 3.6 评审回归（RG）

| 编号 | 用例 | 期望 |
|---|---|---|
| RG-01 | 在自身回调里销毁 Listener | 不 UAF；线程 detach 后自行清理，槽位释放，订阅者可再挂到新 Listener |
| RG-02 | 另一线程阻塞在 lossless Publish 时析构 Publisher | Shutdown 唤醒并等待阻塞调用离开后才释放（ASan 无报告） |
| RG-03a | MapSegment 封印校验 | 非普通文件、未封 F_SEAL_SHRINK 的 fd 返回 kCorrupted |
| RG-03b | 订阅方传未封印通知段 | 发布者 Reject(kCorrupted)；对端 ftruncate 后发布者不 SIGBUS |
| RG-03c | 发布方传未封印连接段 | 订阅者拒绝并断开 |
| RG-04a | 8 线程 lossless 发布 | 收发数相等，`return_ring_full`=0，`bad_returns`=0，段数 ≤3（无块泄漏） |
| RG-04b | 发布者不排空回收环 | 订阅者暂存溢出的归还（计数 `return_ring_full`），环有空间后按序冲刷，不丢块 |
| RG-05 | 发布者正常关闭时队列中仍有样本 | 剩余样本仍可按序 Take，释放后 held=0 |
| RG-07 | 投递写索引被篡改到远超容量 | Take 立即返回（<100ms），判定连接损坏并断开（`corrupted_connections`=1） |
| RG-08 | 重复宣告同一段 id | 断开发布者；已 Take 的样本映射在 Release 前保持可读 |
| RG-11 | 并发析构 Subscriber 与 Listener ×50 | 无数据竞争（TSan） |

### 3.7 运行时行为约定（第三、四轮评审，RB-13~21、RG-20~42、PL-11~13 验证）

**服务目录与配置优先级（M3/O6/M14/M15/O7）**

- 统一规则：显式选项（`RuntimeOptions`）> 环境变量 > 默认值，root、domain、group 三项相同。

| 项 | 选项 | 环境变量 | 默认 |
|---|---|---|---|
| 根目录 | `RuntimeOptions::root_dir` | `IBMW_SHM_ROOT` | Linux：`/dev/shm`（存在且可写时），否则 `/tmp`；OHOS（`__OHOS__`，HongMeng 或 Linux 内核）：无默认，Init/Publisher/Subscriber 返回 `kInvalidArg` 并在 stderr 提示必须显式指定 |
| domain | `RuntimeOptions::domain` | `IBMW_SHM_DOMAIN` | `default` |
| 共享组 | `RuntimeOptions::group`（`std::optional<gid_t>`） | `IBMW_SHM_GROUP`（十进制 gid，非数字即 `kInvalidArg`） | 无 |

- 默认根目录是固定路径，不读取 `XDG_RUNTIME_DIR`/`TMPDIR` 等按进程变化的环境，同一用户的所有进程必然相遇；`/dev/shm` 是 tmpfs，不受 systemd-tmpfiles 对 `/tmp` 的老化清理。
- 服务目录 `<root>/ibmw_shm.<owner>.<domain>`：owner 无组时为 euid（目录 0700，socket 0600），有组时为 `g<gid>`（目录 02770：先 chown 到该组再 chmod，setgid 使其中新建文件继承该组；socket 在 rename 公开前显式 chown 到该组并 chmod 0660，失败则 Publisher 返回 `kPermission`/`kSystem`，不会公开一个对方连不上的 socket）。已存在的本用户目录被收紧为上述模式；他人建的目录（组模式下）必须属组一致、others 无任何权限、组有 rwx，且本进程实际可读写（`access`，附加组也算），否则 `kPermission`（RG-38/39）。
- 不同 uid 的进程只有设置同一个 group 才能互通；否则各用各的目录。组成员身份的判定（第四轮评审 M-d）：对端 SO_PEERCRED 的 egid 等于该组即可；内核支持 `SO_PEERGROUPS`（Linux ≥ 4.13，`getsockopt` 返回对端在 connect/listen 时的附加组列表，最多取 256 个）时附加组成员也被接受。`SO_PEERGROUPS` 不可用的内核（或 HongMeng 若未实现）上，**跨 uid 的进程必须以该组为有效 gid 运行**（`setgid`/`newgrp`/`sg`，或服务配置的主组），只在附加组中会被拒（日志 "credentials not allowed"）。root（uid 0）对端始终被接受。Init 时若发现同 domain 下其他属主的目录，stderr 打印说明（"... serves domain ... for another user or group ..."），便于诊断"两个进程不互通"。
- 服务目录最长 63 字节（socket 路径须放进 `sun_path`，含 7 位 pid）；超出时 Runtime::Init、Publisher、Subscriber 均返回 `kInvalidArg`，stderr 给出实际长度、上限与根目录可用长度，不再出现"连接全部静默失败"。
- systemd `RemoveIPC=yes`（logind 默认）会在用户最后一个会话退出时删除该用户在 `/dev/shm` 下的文件。系统服务用户（uid < 1000）不受影响；以普通用户运行的长期服务应设 `RemoveIPC=no`，或使用显式 `IBMW_SHM_ROOT`（如 `/run/<service>`）。服务目录被删除时运行时会自动重建并重扫（下条），但删除期间的发现会延迟。

**发现（M1/M2）**

- connect 返回 EAGAIN（发布者 listen backlog 满）时，在控制线程定时器上重试：1ms 起倍增，上限 500ms，最多 16 次（计 `SubscriberStats::connect_retries`），不阻塞控制线程；Hello 发送遇到背压同样重试。
- inotify `IN_Q_OVERFLOW` 时全量重扫服务目录；服务目录被删除/移走（`IN_DELETE_SELF`/`IN_MOVE_SELF`）时重建目录、重新 watch 并重扫，失败按 10ms 起倍增（上限 1s）重试。该重试与下条的重扫都是 RuntimeImpl 里的截止时间字段，不是分配出来的定时器，内存不足时也不会丢（第四轮评审 L-4，RG-42）。
- 发现失败（处理 inotify 事件、扫描目录、向订阅者分发或建立连接时内存不足、opendir/readdir/inotify read 出错、socket()/AddFd 失败）时安排一次全量重扫，10ms 起倍增、上限 1s，一次无错扫描后退避复位（第四轮评审 M-a，RG-33）。被发布者拒绝（凭据、Reject）不触发重扫，避免紧密重连循环。
- 控制线程仅在有定时器（重试、隔离轮询）或待办重扫/重建时设置 epoll 超时，空闲时仍为零唤醒（LS-09）。

**控制消息背压与前向兼容（H1/M6）**

- 控制 socket 满（EAGAIN/ENOBUFS）是背压，不是断开：消息进入每连接发送队列，EPOLLOUT 时按序发出（计 `deferred_sends`）。ENOBUFS/ENOMEM 是内核缺 socket 内存而非 socket 满，EPOLLOUT 会立即且持续触发：此时改为 10ms（`kNoBuffersRetryMs`）定时重试，定时器分配失败才退回 EPOLLOUT（第四轮评审 L-2，RG-36/37）。队列上限 `kMaxSegmentsPerPublisher + 64` = 4160 条（每条 ≤32 字节 + 可选 fd）；协议上每方向在途消息不超过 1 + 4096，合规对端不可能触顶。触顶说明对端停止读取：连接按"非有序断开"处理（计 `send_queue_overflows`，发布方随后隔离该连接持有的块）。
- 未知消息类型（`MsgType` 超出已知范围）计 `unknown_messages` 并忽略（随附 fd 关闭），连接保留。前向兼容约定：新消息必须 ≤ `kMaxMsgSize`、附带 fd ≤ 8，且新行为必须先经握手协商，不得依赖旧版本对新消息的处理。magic 错误、已知类型报文过短仍视为协议违例并断开。
- 订阅者放弃一个连接（自身发送失败、映射段失败、内存不足、发布者违例）时：没有持有块则写 `closed` 后断开（有序）；持有块则只 `shutdown(SHUT_RDWR)`，**不写** `closed`，连接作为孤儿保留映射直到最后一个 Release 才写 `closed`（迟到有序关闭）。发布者因此立即看到挂断并隔离这些块，lossless 发布不会再等一个无人读取的环（第四轮评审 M-c，RG-35）。订阅者对同一发布者的重连可与该孤儿并存（`known_paths_` 在挂断时清除，下次扫描/inotify 事件即可重连）。
- 订阅者 Shutdown 在控制线程上（与处理 Welcome 同一线程）给已有连接段的连接写 `closed`；此后才到的 Welcome 不回 ConnAck，直接在其连接段写 `closed`：从未投递过的连接按有序关闭处理（第四轮评审 M-b，RG-34）。

**隔离（H1）**

- 有序关闭：订阅者在关闭前以 release 序设置连接段 `ConnHeader::closed`；发布者在挂断时以 acquire 序读取，置位即立即回收（RB-15）。
- 非有序挂断（崩溃、socket 被关、队列溢出）：该连接未归还的块进入隔离，不再借出（`quarantined` 累计、`quarantined_chunks` 当前值），连接段映射保留以便之后读 `closed`。确认对端进程已死后才回收（计入 `reclaimed`）：
  - 首选 pidfd（挂断时按 SO_PEERCRED pid 打开，注册到 epoll，进程退出即可读）；
  - pidfd 不可用（旧内核、沙箱 ENOSYS/EPERM）时用 `kill(pid, 0)` 轮询，10ms 起倍增、上限 1s；僵尸进程对 kill 仍"存在"，父进程回收后才判死；
  - 只有 `kill` 返回 ESRCH 才算消亡。EPERM（对端属其他 uid 且本进程无 CAP_KILL）、EACCES（SELinux 等安全模块）及其他错误说明不了任何事，且之后也不会改变：该条目转为不可判定并停止轮询（第四轮评审 L-8，RB-20），而不是每秒白查一次直到发布者析构；
  - 无法判定（pid 为 0、对端在其他 pid 命名空间、对端就是本进程、kill 被拒、或 `PublisherOptions::peer_death_check=false`）：计 `unverifiable_peers` 并记日志一次，仅 `closed` 置位或发布者析构时释放。
  - 死亡判定评估（第四轮评审）：Linux 上 pidfd/`kill(pid,0)` 的 ESRCH 只在进程不存在或对本进程不可见时出现，不可见的 pid 命名空间里 SO_PEERCRED 的 pid 本就是 0（已归为不可判定），因此不会把活着的对端误判为死亡；剩余风险是 pid 复用（只会多隔离）以及未验证的平台（HongMeng 内核的 pidfd/kill 语义未在实机确认）。为此提供 `PublisherOptions::peer_death_check`（默认 true）：关掉后从不查询对端进程，隔离块只靠有序关闭或发布者析构释放（RB-21），供无法信任 pid 语义的部署使用；不再引入更复杂的机制。
- pid 复用说明：pidfd 在挂断时打开，此时若 pid 已被复用，判定会延迟到复用进程退出（只会多隔离，不会误回收）；kill 轮询同理，复用进程"活着"即继续隔离。
- 隔离只占用发布者自己的池：池耗尽时 Loan 按正常规则增长或返回 `kNoMemory`，并在有隔离块时记一次日志（"... chunks are quarantined ..."），不会死锁；`Stats()` 先清理已判死的隔离再报告。
- 未确认死亡前绝不复用：宁可多占内存，也不让订阅者正在读的块被改写。发布者自身的失败（池增长时为连接建跟踪表内存不足）同样走隔离而不是直接回收（第四轮评审 H-1，RG-31）。隔离所需内存（`Quarantine` 条目与 `quarantine_` 容量）在接受连接时预先分配，断开时无需分配。
- 直接回收（`CloseConnLocked(…, true)`/`ReclaimAllLocked`）只用于：对端已写 `closed`（有序关闭）、隔离结束（对端已死或迟到有序关闭）、尚未投递任何块的握手阶段失败，以及**协议违例**（投递读索引越界或越过写索引、回收环索引越界、magic 错误/已知类型报文过短）。违例方因此失去对它自己持有块的保护：这些块可能被重新借出并改写，违例方读到什么是它自己的事（第四轮评审 M-e）。其他订阅者不受影响：回收只撤销违例连接自己的引用，同一块若也投递给了别的订阅者，在它们归还前引用计数不归零，不会被复用。合规订阅者到不了这条路径：它的 `delivery_read` 只经 CAS 从 r 推进到 r+1 且 r < write，归还句柄按序写入回收环且环有空余才写（满了暂存，RG-04b），控制消息只在握手后按协议发送；伪造/重复归还只计 `bad_returns`、不断开（RB-03）。

**封印与段校验（M4/M5）**

- 内核不支持 `F_SEAL_FUTURE_WRITE`（Linux < 5.1）时默认降级：告警一次，`PublisherStats::read_only_enforced`=false、`unsealed_segments` 计数；`PublisherOptions::require_read_only=true` 时改为失败（Loan/预分配返回 `kSystem`，不建段）。
- 收到的段 fd 必须在 tmpfs 上（`fstatfs` 为 `TMPFS_MAGIC`，memfd 在 Linux 与 OHOS 上均满足），hugetlbfs 等被拒为 `kCorrupted`。

**内存不足（M7，第四轮评审 M-a 更正）**：第三轮记录的"均捕获并降级"并不成立：Publisher::Shutdown 在 noexcept 函数里复制 `conns_`，~RuntimeImpl 用会分配的 Post 停止控制线程，控制线程的 HandleInotify/OfferPublisher/ScanAll/ScanFor/Rewatch 与命令、定时器闭包没有任何 catch，Call 的闭包抛异常时调用方永远等待，这些都可能 `std::terminate` 或丢失发现。现在：
- 控制线程每个命令与定时器在 try 中运行（`RunGuarded`，记日志后继续）；`Call` 通过共享 promise 把闭包的异常在调用方重抛，排队失败（bad_alloc）则重试，因此不抛异常的闭包使 `Call` 不抛异常（RG-32）。
- 发现路径全部 noexcept，失败即安排退避重扫（见"发现"，RG-33）；目录重建的重试不再依赖分配（RG-42）。
- Publisher/Subscriber::Shutdown 在控制线程上就地遍历 `conns_`，不复制（RG-40）；Runtime 停止用原子标志 + eventfd 写，不分配（RG-41）。
- 仍会因内存不足失败但不终止的地方：接受连接（拒绝该连接）、池增长时为某连接建跟踪表（断开该连接，块隔离，RG-31）、Loan 建段（`kNoMemory`）。

**新增计数**：`PublisherStats`：`unsealed_segments`、`quarantined`、`quarantined_chunks`、`unverifiable_peers`、`unknown_messages`、`deferred_sends`、`send_queue_overflows`；`SubscriberStats`：`unknown_messages`、`deferred_sends`、`send_queue_overflows`、`connect_retries`。

**新增选项**：`PublisherOptions::peer_death_check`（默认 true，见"隔离"）。

**fork**：fork 后子进程不得访问父进程的任何 Sample（Take 得到的指针、Loan 得到的块），也不得继续使用父进程的 Publisher/Subscriber/Runtime：控制线程不随 fork 复制，引用计数与连接属于父进程，子进程对样本的读写与 Release 都没有定义。子进程需要通信时应在 exec 后或以全新进程重新创建对象。

**测试故障注入**（`detail::fault`，仅测试使用）：`send_would_block`（接下来 N 次发送返回 EAGAIN）、`send_no_buffers`（N 次 ENOBUFS）、`send_queue_limit`（发送队列上限覆盖值）、`map_segment_fail`（N 次映射失败）、`grow_bad_alloc`、`offer_bad_alloc`（N 次 bad_alloc）、`no_future_write_seal`、`no_pidfd`、`kill_eperm`、`subscriber_shutdown_pause`（Subscriber::Shutdown 中的回调）。测试二进制与对端还替换了全局 operator new（`test/fail_alloc.cc`）：`test::FailAllocations(n)` 让调用线程接下来 n 次分配抛 `std::bad_alloc`，用于覆盖没有专门桩的分配。

## 5. 已知限制（测试未覆盖或待后续阶段）

- 空闲段收缩/退役未实现（W06 剩余）；长稳 72h、aarch64/OHOS 实机、fuzz、模型检查属于后续里程碑（W17/W22/W24）。
- 启动残留 GC 仅覆盖 socket 文件（memfd 随进程消亡由内核回收，无 /dev/shm 残留）。
- 评审遗留（已评估，后续阶段）：发布者重启后的自动重连依赖 inotify 新 socket 事件（同路径不复用）；fork 后子进程不可继续使用父进程的 Runtime；Hello 超时未限时（恶意对端只占 1 个连接名额，上限 1024）。
- 隔离依赖对端 pid：对端在其他 pid 命名空间（容器）或沙箱禁止 pidfd/kill 时只能等有序关闭或发布者析构，期间这些块不可复用（`unverifiable_peers` 可监控）。跨 uid 互通需要 root（RG-39 在非 root 时跳过，本机 CI 不覆盖），由 `run_shm_ohos.sh device` 在设备上以 root 运行并要求不得跳过；单用户部分由 RG-29/RG-38 覆盖。
- 订阅者析构前必须 Release 所有已 Take 的样本（API 契约，IBMW 驱动由释放令牌持有订阅对象保证）。fork 后子进程不得访问父进程的 Sample（见 3.7）。
- 第四轮评审 L-3（已评估，未修改）：`QuarantineLocked` 在 `mu_` 下做 pidfd_open/poll/kill/日志 fprintf，可能发生在 Loan/Publish 线程上；`FlushOut` 在 `mu_` 下最多发送 4160 条消息；`ReapQuarantineLocked` 在空闲链表为空时对每个隔离条目 poll。都只在慢路径（断开、背压、池耗尽）发生且有上界，但会拉长这些时刻其他线程 Loan/Publish 的尾延迟。
- 第四轮评审 L-5（已评估，未修改）：connect EAGAIN 重试 16 次用尽后放弃该发布者（记日志），直到下一次扫描（该 URL 有新订阅者、inotify 溢出、服务目录重建）或新 socket 事件才重新发现。同理，订阅者因本地原因（映射失败、内存不足）或发布者违例放弃一个仍存活的发布者后，不自动重扫，避免在被拒时形成紧密重连循环；内存不足、socket()/AddFd 失败等发现阶段的失败则会退避重扫（3.7）。
- 第四轮评审 L-7（已评估，未修改，旧问题）：accept 遇 EMFILE/ENFILE 时直接返回，而 listen fd 仍可读，控制线程会在 fd 耗尽期间忙转。
- 第四轮评审 L-6：`quarantined_now_` 在 bad_alloc 时卡住的路径已随隔离条目预分配一并移除（QuarantineLocked 不再分配），无单独用例。
- 与 IBMW 数据路径的集成测试见 IBMW 侧测试（W10/W11 阶段补充）。
- 块在同一地址循环复用：驱动的 loan 令牌是槽位地址 + 6 位代际标记，旧句柄副本在槽位被重新借出后被拒绝（EXT-25）；仅当其间该槽位恰好经过 64 的整数倍次借出时才可能误认（iceoryx 无此保护）。直接使用 selfdev `Publisher` 的块指针则无代际信息。
- `Subscriber` 侧不得用 `ChunkView` 读取尺寸（头部在发布者可写内存中），应使用 `Subscriber::PayloadSize`。
- 组模式信任模型：组目录 02770 不设粘滞位，组内成员可删除/替换彼此的 socket（同组即互信）；组模式下跨 uid 对端的崩溃回收依赖 pidfd（kill(pid,0) 跨 uid 返回 EPERM，对端记为不可验证，块隔离到发布者退出）。
- OHOS/HongMeng：root 进程 setresuid 到普通 uid 后**不会**自动清除 capability（Linux 会），以 root 启动再降权的服务必须自行 capset 清零，否则 DAC 校验形同虚设。实机验证为 root shell（静态链接，以及 §6.6 的 .so 插件）、由 root 降权的普通 uid（§6.7，仍在 su 域）和 HAP 进程内（§6.8，调试签名 `debug_hap` 与发布签名 `normal_hap` 域，同一 HAP 的原生子进程之间；HAP 内 exec 被禁止，依赖 exec 的 3 个 EXT 跨进程用例未在 HAP 内运行，跨进程由 runner 覆盖）；设备内核会静默放宽普通 uid 对 CPU 12~19 的绑核请求（§6.7）；服务目录（root + `/ibmw_shm.<owner>.<domain>`）不得超过 63 字节，OHOS 必须显式指定 `IBMW_SHM_ROOT`（如 `/data/local/tmp/...` 或应用沙箱目录）。
- 跨 HAP 不支持（设计限制）：不同 HAP 的 uid、挂载命名空间与 SELinux 域隔离，无法经文件系统 socket 会合。可行方向是通过 IPC Kit 传递 fd（另立项）。同一 HAP 内多进程、系统服务之间可用。
- 需要核心（框架维护方）处理的问题不在本仓库修改，记录在仓库外的 `零拷贝自研_核心维护方问题清单.md`（C1~C10；与本文相关的：C9 注册传输驱动不检查重名、初始化取第一个同名驱动，shm_extension 自行检查，见 EXT-61、§6.10；C10 加载 iceoryx_extension 而不启用其驱动时退出报 Fatal，见 §6.10；C7 核心类型 typeinfo 隐藏导致 OHOS 上跨 .so 只能按 `std::exception` 捕获，见 §6.6；C8 `BindCpuForCurrentThread` 不读回亲和性，见 §6.7）。
- 第五轮（独立评审）LOW 已评估、未修改：控制线程 `Call()` 中 `set_exception` 自身抛异常时等待方不被唤醒（实际不可达）。shm_ext 多线程发送竞争同一 gate 计数器缓存行（M12）已于 2026-11-03 通过计数条带化解决，见 §6.5.1；单线程仍比加门前多一对 seq_cst 操作（x86 约 9 ns）。

## 6. IBMW 传输扩展 shm_ext（EXT）

`src/extensions/transport/shm_ext` 是 iceoryx_ext 的替代驱动（驱动名默认 `shm`，可配 `driver_name: iceoryx` 原位替换），URL 与帧格式与 iceoryx 驱动一致：`/transport/<topic>/<type>`、`/transport_zc_pod/...`，ctx-meta 帧头。

### 6.1 运行

```bash
selfdev/shm/scripts/run_shm_ext_tests.sh            # unit
selfdev/shm/scripts/run_shm_ext_tests.sh all        # unit repeat asan tsan
IBMW_CMAKE_ARGS="-DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=/path/googletest-src" \
  selfdev/shm/scripts/run_shm_ext_tests.sh unit     # 离线依赖
```

- 最小配置：只开 `IBMW_BUILD_SHM_EXTENSION`，iceoryx/DDS/其他扩展/CLI/示例/protocols/ros2 types 全关，CI 无需第三方 SDK；只构建目标 `ibmw_extensions_shm_ext_test`（及跨进程子进程 `ibmw_shm_ext_peer`）。
- `IBMW_CMAKE_ARGS` 追加在最后，可覆盖默认项。其余变量 `BUILD_ROOT`（默认 `<repo>/build-shm-ext`）、`OUT_DIR`、`REPEAT`、`JOBS`、`GTEST_FILTER`、`TEST_TIMEOUT`、`TSAN_CC/TSAN_CXX` 同 §1。
- IBMW 顶层对测试构建加 `--coverage`，除非设置 `ADDRESS_SANITIZER`/`THREAD_SANITIZER`；gcov 计数器非原子会成为 TSan 噪声，脚本 asan/tsan 阶段自动传这两个开关。
- 全量 IBMW 构建中直接运行：`<build>/ibmw_extensions_shm_ext_test`。
- 用例 EXT-53 依赖核心测试的 `fail_alloc.cc`（`test::FailAllocations`），shm_ext 的测试目标直接编入该文件。代价：该文件替换全局 `operator new/delete`，ASan 构建下测试二进制（核心库测试与对端、shm_ext 测试同样如此）不再经过 ASan 自己的 new/delete 拦截器，因此 `new`/`free` 这类配对错误（alloc-dealloc-mismatch）在这些测试中查不出；越界与释放后使用基于 malloc 仍可检测。
- `ShmCtxMetaPublisher::Publish` 的 true 不代表库接受了发布：它只用 `TransportDriver` 基类接口，`PublishLoaned` 无返回值。发布被拒时块仍被归还。需要确切结果的调用方自行 loan 后调用 `ShmTransportDriver::TryPublishLoaned`。

ibmw_gen 冒烟（`selfdev/shm/scripts/run_shm_gen_smoke.sh`）：用 `selfdev/shm/test/gen/` 下的 `loaned_shm.ibmw.yaml`、`direct_shm.ibmw.yaml` 生成两个工程，对已安装的 ROS2 版 IBMW 构建，在全新的 `IBMW_SHM_ROOT` 上运行每对发布者/订阅者后发 SIGINT。判定：两个进程都以 0 退出，且订阅日志中至少收到一条消息。

扩展 YAML 选项（`extensions: shm_extension: options:`；位置项统一为 选项 > 环境变量 > 默认值）：

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `driver_name` | 字符串 | `shm` | 驱动名（路由按名）；`iceoryx` 为原位替换。驱动槽位与名字无关，恒为 `shm` |
| `domain` | 字符串 | `$IBMW_SHM_DOMAIN`，否则 `default` | 至多 32 字符，不含 `/` |
| `root_dir` | 路径 | `$IBMW_SHM_ROOT`，否则 `/dev/shm`（存在且可写），否则 `/tmp` | OHOS 无默认：两者都未设置时 Initialize 抛错并说明须显式指定 |

驱动选项（`transport: drivers:` 中的同名驱动）：`listener_thread_name`、`listener_thread_sched_policy`、`listener_thread_bind_cpu` 作用于该驱动 bus 的全部监听线程（所有订阅类型、监听池的每个线程），在每个线程的首个回调之前生效（EXT-33）。绑核由核心 `BindCpuForCurrentThread` 完成，只检查 `sched_setaffinity` 的返回值；OHOS 设备上普通 uid 的请求可能被内核静默放宽（§6.7），驱动不会察觉。

Start 前的样本（EXT-34~37）：订阅在 Init 态注册时即连接，但 `Start()` 之前不挂到监听线程，没有回调运行。其间发布的样本按订阅自身策略留在队列：latest（默认）只保留最新一条，lossless 最多保留队列容量（256）条，满后生产者像遇到慢消费者一样阻塞（lossless 发布超时规则不变）。`Start()` 后监听线程立即投递这些样本。未 Start 即关闭时队列被丢弃，阻塞的生产者被释放。同一驱动的 `Send()` 在 Start 前本就被拒绝，所以只有 loan、其他驱动或其他进程会在 Start 前发布。

初始化报告（`GenInitializationReport`）另含：`domain`（实际生效的 domain）、`require read only`、`send failures`、`send failure logs suppressed`，以及 selfdev 健康计数（报告时刻存活的发布者/订阅之和）。

### 6.4 iceoryx_ext 源码兼容：兼容 API、CLI 与 ibmw_gen

**兼容 API**：`shm_ext/iox_style_publisher.h` 在命名空间 `ibmw::extensions::shm_extension` 中提供与 `iceoryx_ext/iox_style_publisher.h` 同名、同签名、同语义的类与函数：`IoxLoanedSample<T>`、`IoxStylePublisher<T>`、`CreatePodPublisher<T>`、`RegisterPodSubscriber<T>`、`IoxRawPodPublisher`、`CreateRawPodPublisher`、`RegisterRawPodSubscriber`、`IoxCtxMetaLoanedBuffer`、`IoxCtxMetaPublisher::borrow_loaned_buffer(ctx, payload_size)`、`CreateCtxMetaPublisher`、`IoxCtxMetaTypedPublisher<T>`、`CreateCtxMetaTypedPublisher<T>`，以及 R8.2 检查 `IbmwR82SlotMixCheck`。`IceoryxTransportDriver` 是 `ShmTransportDriver` 的别名。唯一的有意差异：`publish()` 如实返回结果（无效样本、重复/过期 loan、外来句柄都返回 false），iceoryx_ext 对有效样本恒返回 true。为此驱动新增 `ShmTransportDriver::TryPublishLoaned`（返回 bool，`PublishLoaned` 委托给它），`ShmPublisher::Publish`/`PublishSlot` 改为返回 bool，`ShmRawPodPublisher::Publish` 返回真实结果。外来句柄的 `publish()` 把块交还借出它的驱动（EXT-58）。用例 EXT-48~52、EXT-58。

**ctx-meta 发布不上报**：shm_ext 没有实现 Reporter V1（`ibmw_reporter_v1`），ctx-meta loan 的模式恒为 `LoanMode::kCtxMetaThenPayloadUnreported`，经 `borrow_loaned_buffer`、`LoanSample`、`LoanSerializedSample` 发布的 ctx-meta 帧不进入 host reporter。iceoryx_ext 在定义 `IBMW_ENABLE_REPORTER_V1` 且 host 提供 reporter 时会上报，这是迁移时的可观测性差异；发布结果只能从 `publish()` 返回值与 `Stats()` 获知。

**CLI**：`ibmw topic pub ... --shm` 选择 shm 驱动（加载 `libibmw_shm_transport.so`，扩展名 `shm_extension`）。选项与扩展 YAML 键一一对应：

| CLI 选项 | YAML 键 | 取值 |
|---|---|---|
| `--shm-init-size` | `shm_init_size` | 1 ~ 268435456（256 MiB，shm 最大 loan，即 kMaxLoanSize），缺省 1024；与 `--iceoryx` 共用，`--iceoryx` 下仍为 1 ~ 4294967295 |
| `--shm-runtime-id` | `runtime_id` | 缺省为 CLI 身份名 |
| `--shm-domain` | `domain` | 非空 |
| `--shm-root-dir` | `root_dir` | 非空 |
| `--shm-group` | `group` | 0 ~ 4294967294 的数字 gid |
| `--shm-max-bytes-per-publisher` | `max_bytes_per_publisher` | 正整数 |
| `--shm-prefault` | `prefault` | 开关，给出即 true |
| `--shm-require-read-only` | `require_read_only` | 开关，给出即 true |

`--shm-*` 只能与 `--shm` 同用，`--iceoryx-runtime-id` 只能与 `--iceoryx` 同用。`driver_name` 不提供 CLI 选项：CLI 按驱动名 `shm` 路由，改名会使路由失效。`--shm-init-size` 上限在解析时检查，超过 256 MiB 直接报错，不会等到首次 loan 才失败。测试：`ibmw_topic_cli_test` 的 `IceoryxAndShmDriversMapToTheirExtensionOptions`、`RejectsShmOptionsForOtherDriversAndInvalidValues`。

**ibmw_gen**：新增传输插件 `transports/shm.py`（与 `transports/iceoryx.py` 对应），支持 `direct_shm_publisher`/`direct_shm_subscriber`（`shm_ext/shm_transport_driver.h` 位于 `IBMW_R1_EXEMPT` 锚内）与 `transport: shm` 的 `loaned_publisher`/`loaned_subscriber`（统一四文件布局，仅 strict 零拷贝）。schema 接受 `wire.shm.msg_type`（仅用于日志，对应 `shm_msg_type`），`direct_shm_*` 隐含 `transport: shm`，shm 计入 SHM 能力传输（不触发 R8.2 错误）。生成的 CMake 链接 `ibmw::extensions::shm_ext`，不查找 `iceoryx_posh`；生成的配置自动加入 `shm_extension`（选项取项目 `shm_driver.extension_options`），消息驱动为 `- type: shm`，没有 RouDi 前置说明。`direct_shm_*` 模块的主题同样写入配置的 `messaging` 段（`publishers`/`subscribers` 带 `enable_drivers: [shm]`）。同一应用混用 iceoryx 与 shm 模块时 `config_gen` 报错（shm 与 iceoryx 使用相同 URL，按优先级选驱动会把 shm 模块静默移到 iceoryx 上）；需分到不同应用或统一传输。`migrate_yaml` 支持 `shm_msg_type`。`ibmw-gen import --target shm` 输出 `<pkg>_shm_backend_metadata.json` 与 `<pkg>_shm_lowering_plan.json`（与 iceoryx 相同，仅元数据）。测试：`src/tools/ibmw_gen/tests/test_shm_plugin_emit.py`；端到端冒烟见 §6.1 的 `run_shm_gen_smoke.sh`。

| 项目 | iceoryx_ext | shm_ext |

| 头文件 | `iceoryx_ext/iox_style_publisher.h` | `shm_ext/iox_style_publisher.h` |

- 设备速度在运行中变化（有两种状态，`gate_pair` 约 25 ns 或约 42 ns，同一进程内稳定，原因未查），表中的 min..max 主要反映这一点，请看配对差。约 42 ns 状态下 `pod_loan_*` 配对差约 +43~+48 ns；此前一次 9 轮运行在约 25 ns 状态的轮次里 `pod_loan_*` 约 +20~+30 ns。两种状态下差值都接近 `gate_pair` 本身，这是把它归因于门的依据。
- 设备的噪声下限不低：对照 `send` 64 B 配对差 +69 ns（4 KB 为 −0.8 ns），`ctx_loan_publish` 约 +120 ns，都超过门的代价，原因未查明。因此设备上的单线程差值量级可信，具体数字不能当精确值，`pod_loan_*` 的 +45 ns 单看并不超过 `send` 64 B 的偏差。
- 设备多线程：4 线程约 −25%（3.70→2.75、3.69→2.76 Mops/s）；8 线程两边都塌到约 2 Mops/s，新树反而略高（+7%），此时门对照也只有约 4 Mops/s，这一档不能说明新树更好，原因未查明。

未测量：跨进程订阅者下的代价；Shutdown 竞争路径；真实负载（写满载荷、实际消息频率）下的占比；单独去掉门、其余不变的版本；设备固定频率下的结果（共享设备，未改调频设置）。

#### 6.5.1 操作门计数条带化（2026-11-03）

上表显示多线程退化来自门计数：`scale_gate_pair` 在 x86 上无论几个线程都只有约 34 Mops/s，即所有线程争同一缓存行。`ShmOperationGate` 因此改为 16 个各占一个缓存行的计数条带，`accepting_` 单独一行。线程第一次使用时按轮转分到一个条带（常量初始化的 `thread_local`），lease 记住自己的条带并在那里释放；`WaitIdle`/`Active` 对各条带求和。正确性依据见 `shm_bus.cc` 中 `TryAcquire` 上方注释：被拒的获取只会让和偏大，不会偏小。

条带选择的取舍：曾试过按栈地址哈希（单线程零额外开销），但不同线程会随机撞到同一条带，设备上 8 线程门对照 160 对 209 Mops/s；最终采用轮转，≤16 线程不冲突、结果可预期，代价是设备单线程约 +6 ns。

### 6.6 插件以 .so 形式的实机验证（`run_shm_ohos.sh dynamic`）

其余设备阶段都是全静态二进制，不经过设备的动态链接器。`dynamic` 把 `libibmw_shm_transport.so`（真实插件）放到设备上运行，构建目录为 `${OUT}/dyn`，不影响静态阶段。

```bash
selfdev/shm/scripts/run_shm_ohos.sh dyn-build              # 交叉构建、检查 INTERP/NEEDED、写 logs/dyn-tls.txt
REPEAT=5 selfdev/shm/scripts/run_shm_ohos.sh dyn-device    # 双进程 runner + 动态链接的 EXT（单次 + 乱序 ×REPEAT）
DYN_BENCH_ROUNDS=15 selfdev/shm/scripts/run_shm_ohos.sh dyn-bench  # static / pie / so 三组基准交替
REPEAT=5 selfdev/shm/scripts/run_shm_ohos.sh dyn-uid       # 同一 runner 与 EXT 以 RUN_UIDS 中每个普通 uid 运行，见 §6.7
selfdev/shm/scripts/run_shm_ohos.sh dyn-clean              # 删除设备上的 DYN_DEVICE_DIR / DYN_DEVICE_ROOT
selfdev/shm/scripts/run_shm_ohos.sh dynamic                # dyn-build dyn-device dyn-uid dyn-bench dyn-clean
```

变量：`DYN_DEVICE_DIR`（默认 `/data/local/tmp/ibmw_shm_dyn`）、`DYN_DEVICE_ROOT`（默认 `/data/local/tmp/ibd`，保持短以满足 63 字节限制）、`DYN_BENCH_ROUNDS`（默认 15）、`BENCH_ARGS`、`BENCH_CPUS`。结果在 `${OUT}/logs/dyn-*`。

构建方式：

- 树内 core、selfdev 都是 STATIC 目标（`-fPIC`），所以“动态构建”指：插件 .so 和各可执行文件各自静态包含它们（与生产相同），可执行文件为 PIE，由设备的 `/lib/ld-musl-aarch64.so.1` 加载。
- 使用 `OHOS_STL=c++_shared`，并把 SDK 的 `libc++_shared.so` 推到设备、用 `LD_LIBRARY_PATH` 指向。引擎与插件之间传递 `std::string`、`std::function`、`shared_ptr`、`YAML::Node` 和异常（`MW_REQUIRE`），必须共用一份 libc++/libc++abi；不用设备上的副本，因为它的版本不一定与 SDK 头文件一致。
- 新目标在 CMake 选项 `IBMW_BUILD_SHM_EXT_DYN_CHECK`（默认 OFF）之后，不安装。

检查内容：

- `ibmw_shm_ext_dyn_runner`（`test_peer/`，不链接插件）：发布、订阅各一个进程，都用核心 `ExtensionLoader` dlopen 插件，再把扩展对象注册给 Engine（`ExtensionBus` 自身从不卸载，无法测卸载）。20 个发送线程各用一个主题（多于 16 个条带），其中 6 个在 dlopen 之前创建（插件以 nodelete 链接、不会解除映射，所以只有第一周期的这 6 个线程真正早于首次 dlopen）。lossless 配置下订阅端必须在每个主题上按序收到 1..2000，共 40000 条，errors=0。每周期结束做 `UnLoadExtension()`（destroy + dlclose），同一进程再做第二周期。runner 关闭了 `runtime_graph`：它的默认目录 `/tmp/ibmw-<uid>` 在设备上无法创建（Engine 初始化抛错），与插件无关。
- 60 个 EXT 用例：动态链接（PIE + `libc++_shared.so`），但**插件源码仍编译进测试**，没有链接 .so。用例需要插件未导出的符号（`ShmExtension`、selfdev `shm::Runtime`、`shm::test::FailAllocations`），且要与插件共用同一份 selfdev 状态。
- `ibmw_shm_ext_bench_so`：与 `ibmw_shm_ext_bench` 同一份源码，但链接 .so，门与 loan/publish 路径在 .so 内执行（`nm -D` 中 `TryAcquire`、`TryPublishLoaned` 为 U）。为此插件导出 `shm_extension::SetShmExtensionLogger()`（`g_logger` 本身不导出），基准中等待订阅者的方式改为只用导出 API（持续发布直到订阅端收到）。
- 异常与 C++ 运行时绑定（runner 在两个周期之后执行，`DYN_THROW` / `DYN_ABI` 行，pub、sub 各一次）：
  - 在两个周期之后（插件以 nodelete 链接，若放在之前，第一周期就没有早于首次 dlopen 的发送线程）加载插件，以未知的驱动 `benchmark_profile` 初始化 Engine。`ShmTransportDriver::Initialize`（插件代码）的 `MW_REQUIRE` 抛 `ibmw::common::util::IbmwException`，引擎的传输子系统（可执行文件代码）回滚后重新抛出。扩展自身的选项不行：插件内的核心 `ExtensionBase` 会吞掉 `OnInit` 的异常，引擎再抛自己的。
  - 判定：在可执行文件中以 `std::exception` 捕获，动态类型名为 `N4ibmw6common4util13IbmwExceptionE`，消息完整（含 `Shm benchmark delivery controls`），没有 `std::terminate`。随后 `UnLoadExtension()`。
  - `typed_catch` / `typed_cast`（只记录，不判定）：可执行文件按 `IbmwException` 类型的 handler（在 `std::exception` 处理器内 `throw;` 再捕获）/ `dynamic_cast` 能否命中。工程统一 `CMAKE_CXX_VISIBILITY_PRESET hidden`（顶层 `CMakeLists.txt`），可执行文件与插件各有一份本地（`nm` 为 `d`、不在 `nm -D` 中）的 `_ZTIN4ibmw6common4util13IbmwExceptionE`。x86 libstdc++ 按名称比较 typeinfo，两项均为 1；设备 libc++ 按地址比较，两项均为 0。即：**OHOS 上插件抛出的 ibmw 核心异常，跨 .so 只能按 `std::exception` 捕获**。这是核心构建策略，不是插件缺陷，已作为 C7 交给框架维护者（§5）。插件自身需要跨 .so 使用 RTTI 的类型（如 `ShmTransportDriver`，供 `shm_loaned_pod` 的 `dynamic_cast`）以 `IBMW_SHM_EXPORT` 导出，`nm -D` 中为 `D`：基准启动时对 `TransportDriver*` 做 `dynamic_cast<ShmTransportDriver*>`，失败即退出，`bench_so`（链接 .so，与样例相同）打印 `DYNCAST_SHM_DRIVER=PASS`。只 dlopen、不链接插件的宿主无法引用该 typeinfo，不适用。引擎取驱动能力接口（`TransportShutdownCapabilityV1` 等）由插件内 `static_cast` 后交出（`shm_extension.cc`），不依赖跨 DSO 的 RTTI。核心唯一在可执行文件一侧对驱动指针做的 `dynamic_cast` 是 `IBMW_ENABLE_COMM_TRACE` 下的 `CommTraceSendOverlayV1`（`transport_driver_dispatcher_ops.cc`）；`ShmTransportDriver` 不实现它，结果总是 nullptr，不受影响。
  - `DYN_ABI`：对 `__cxa_throw`、`__gxx_personality_v0`、`__cxa_thread_atexit`、`__emutls_get_address`、`_Znwm`、`_ZTISt9exception`，分别在可执行文件（`RTLD_DEFAULT`）与插件句柄上 `dlsym` + `dladdr`，两者必须是同一 DSO，且不是设备的 `chipset-sdk-sp/libc++.so`。插件句柄上的 `dlsym` 按其依赖顺序查找，而插件自身的重定位先走全局作用域，所以插件一列是近似，不是其重定位的实际结果。
  - `dyn-device` 要求 2 行 `DYN_THROW ... result=PASS` 且没有 `DYN_ABI ... result=FAIL`。

卸载的结果与 `-z nodelete`：

设备的 musl 在 dlclose 时真正解除映射。首次运行时订阅进程第一周期 PASS、`mapped_after_unload=0`，第二周期初始化时 SIGSEGV（退出码 139）。用 `LD_PRELOAD` 的信号处理库定位：崩溃线程 `comm` 为 `ibmw_shm_ctl`，`pc` 落在已解除映射的旧地址。原因是进程级 selfdev 运行时及其控制线程按设计存活到进程退出（`g_instance` 有意泄漏），插件卸载时没有人停止它；`~ShmExtension` 在 bus 仍被使用时也有意泄漏 bus。因此插件现在以 `-Wl,-z,nodelete` 链接（`FLAGS_1` 含 NODELETE）。

所以这里的“干净卸载”只表示：destroy 与 dlclose 返回且无崩溃，`IsLoaded()` 为假，第二次加载得到新的扩展对象并收齐全部消息。插件**不会**从进程中解除映射（`mapped_after_unload=1`），控制线程和运行时也继续存在，第二周期复用它们（同名主题被重新创建）。真正可卸载需要插件在卸载时关闭运行时，并处理被泄漏的 bus，本次未做。引擎本身从不卸载扩展（`LeakHandle`），生产路径不受影响。

修复前发布进程已经是 `mapped_after_unload=1`。已知的一条线索：设备的 `/lib/ld-musl-aarch64.so.1` 导出 `__cxa_thread_atexit_impl`，SDK `libc++_shared.so` 弱引用它，插件导入 `__cxa_thread_atexit`（有非平凡析构的 `thread_local`），注册时带上插件的 DSO 句柄；按 glibc 同名接口的语义，这会在注册线程退出前钉住 DSO。若发布进程中有仍存活的线程注册过这类析构，就会出现“发布进程不卸载、订阅进程卸载”。哪段代码、哪个线程注册未查，也未反汇编确认 OHOS musl 的实现，只能算支持性证据，不是结论。

### 6.7 普通 uid 运行与 HAP 签名探测（`run_shm_ohos.sh dyn-uid`）

`dyn-uid` 用 §6.6 的产物（真实插件 .so、runner、动态链接的 EXT 与 peer），在设备上以普通 uid 重跑 runner（发布、订阅两个进程，两周期）和 EXT（单次 + 乱序 ×REPEAT）。需要先 `dyn-build`。变量 `RUN_UIDS`（默认 `2000 20099999`，gid 取同值）：2000 是 shell uid；20099999 位于用户 100 的应用 uid 段（设备上的应用为 2002xxxx），运行前检查该 uid 没有进程，有则打印 NOTE。

降权（`scripts/ohos/run_as.c`，静态链接，随阶段编译并推送）：

- 由 root 启动：`setgroups(0)`、`setresgid`、`setresuid`，然后 `capset` 清空 effective/permitted/inheritable，并清 ambient。HongMeng 内核在 root 改 uid 后保留能力（Linux 会清掉），不清时 `CAP_DAC_OVERRIDE` 仍可进入任何目录。
- exec 之前自检，任何一项不符则退出 125、不运行命令：
  - 三组 uid/gid 都等于目标值；
  - 没有附加组；
  - effective/permitted/inheritable/ambient 均为 0；
  - root 所有的 0700 目录（`DYN_DEVICE_ROOT/deny`）：降权前 root 能在其中创建并删除探测文件（正对照），降权后创建必须以 `EACCES` 失败。
- uid/gid 参数须为非零十进制数（无符号、无多余字符、小于 2^31）。
- 自检通过后打印 `RUN_AS ... result=PASS` 行；阶段要求 runner 两个进程、EXT 两次运行各有该行。
- 不改变的：
  - SELinux 域保持 `u:r:su:s0`（不是 HAP 的域）。
  - 能力边界集保持完整：清空后设备上 exec toybox 以 `EPERM` 失败，原因未确认（toybox exec 后会获得能力，见下；可能与文件能力或域切换有关），普通进程也不清它。
  - 不设置 `PR_SET_NO_NEW_PRIVS`。
- exec 以后的状态：
  - 设备上 `/bin/sh`、toybox 在 exec 后又带上 `CapEff=0x2e`（DAC_OVERRIDE、DAC_READ_SEARCH、FOWNER、KILL；来源未查，推测为文件能力）。
  - 所以阶段另外检查 `DYN_DEVICE_DIR` 中的文件在 exec 后的状态：`run_as ... ./run_as --caps` 必须仍是目标 uid、无附加组、能力集为 0，SELinux 上下文与 root shell 相同。
  - 被测程序自己报告：runner、EXT 测试程序与它启动的 peer 在 `main` 开头各打印一行 `PROC_CREDS`（读自身 `/proc/self/status`：四组 uid/gid、附加组、CapInh/CapPrm/CapEff/CapAmb）。阶段要求每一行都是目标 uid、无附加组、能力为 0，且 runner 日志有 2 行 `bin=runner`，每次 EXT 运行至少有 1 行 `bin=ext_test` 与 1 行 `bin=peer`。
  - 测试程序与它启动的 peer 都直接 exec 该目录中的文件，不经过 shell。
- 目录：
  - uid 只能访问 `DYN_DEVICE_DIR`（0755，root 所有，只读）和自己的 0700 目录 `DYN_DEVICE_ROOT/u<n>`（`TMPDIR`，`IBMW_SHM_ROOT` 与同步目录在其下）。
  - 运行后检查该目录内没有不属于该 uid 的文件；runner 输出由 root shell 写在该目录之外。该检查只看运行结束时留下的文件（EXT 退出时删除自己的临时树，运行中创建又删除的文件看不到）。
  - 每个 uid 结束后检查没有该 uid 的本阶段进程残留（如超时后的 peer），有则失败并 `pkill`。
- 日志：每次运行一个目录 `${OUT}/logs/dyn-uid-<时间>/`，内含 `uid<uid>-{caps,runner,ext-once,ext-repeat,foreign}.log`，失败运行的日志不会被下次覆盖。
- 推送：`dyn_push` 先删除设备上的旧文件，推送后比对大小，产物缺失或推送失败时阶段失败，不会测到旧二进制。

### 6.8 HAP 进程内运行（`run_shm_ohos.sh hap`、`hap-release`）

目的：在真实应用进程（调试签名 `debug_hap` 域或发布签名 `normal_hap` 域、应用 uid）中加载插件 .so，跑 EXT 用例与 runner 的发布/订阅，确认 shm 在应用沙箱内可用。`hap` = `dyn-build` + `hap-build` + `hap-device`；`hap-release` 同上，`HAP_SIGN=release`。`hap-device` 要求 `OUT/hap/sign-mode` 与 `HAP_SIGN` 一致，此前的构建需重新 `hap-build`。

设计：

- HAP 进程不能 exec 任何文件（含 `/system/bin/sh` 与包内文件，均为 `EACCES`），所以测试不以可执行文件运行：
  - NAPI 模块 `libibmw_shm_ext_hap.so`（`test_peer/shm_ext_hap.cc`）提供 `start(cacheDir, repeat, stepTimeout)` 与 `poll()`；
  - 每一步用 `OH_Ability_StartNativeChildProcess("libibmw_shm_ext_hap.so:HapChildMain")` 启动原生子进程，子进程 `dlopen` 被测库（EXT 测试库 `libibmw_extensions_shm_ext_hap_test.so` 的 `ShmExtHapRunTests`，或 runner 库的 `ShmExtDynRunnerMain`），stdout/stderr 重定向到 `<步骤>.log`，结束时原子写 `<步骤>.rc`；
  - 子进程与应用同 uid、同 SELinux 域。
- 步骤：`ext-once`（单次）、`ext-repeat`（乱序 ×`REPEAT`）、runner `sub` 与 `pub` 并发（两周期，超时 300 s）；`TEST_TIMEOUT` 作为每步超时（`steptimeout`）。
- EXT 中启动 `ibmw_shm_ext_peer` 的 3 个用例（`CrossProcessPeerPublishesToDriver`、`CrossProcessDriverPublishesToPeer`、`ShutdownUnblocksSendToStalledRemoteConsumer`）需要 exec，被过滤，所以每次运行 58 个（61 − 3；EXT-61 加入前为 57）；它们在 §6.6/§6.7 中以 root 与普通 uid 运行。
- `TMPDIR` 为 `/data/storage/el2/base`（cache 的上级），使每用例服务目录不超过 63 字节；runner 的 `IBMW_SHM_ROOT` 为 `<cache>/r/s`。
- 子进程等待：父进程不是子进程的父进程（不能 `waitpid`），用 `pidfd_open` + `poll` 发现退出；超时或 `.rc` 出现后 10 s 仍未退出时用 `pidfd_send_signal` 发 SIGKILL（pidfd 打开后不受 pid 复用影响；启动返回到 `pidfd_open` 之间的极短窗口除外）。返回码：`-1` 超时、`-2` 退出但无 `.rc`（崩溃）、`-3` 写了 `.rc` 但不退出、`-4` 无 pidfd 且无 `.rc`（`HAP_STEP` 行的 `pidfd_errno`：ESRCH 表示已退出，其他值表示未被监视、可能仍在运行）。
- 旧结果树用 `nftw(FTW_DEPTH|FTW_PHYS)` 删除，不调用 shell。
- ArkTS 部分（`scripts/ohos/hap/`）：`OpenHarmonyTestRunner.js` 读 `-s repeat`、`-s steptimeout`，调用 `start` 后轮询 `poll`，仅当摘要含 `HAP_RESULT result=PASS` 时 `finishTest` 返回码 0。

排障中发现并已修复的问题（记录见 `${OUT}/logs/hap-inapp-probe-20261103.txt`）：

1. **`libchild_process.so` 抢占 typeinfo**：它导出默认可见的 `_ZTISt9exception`、`_ZTISt13runtime_error` 等（绑定系统 `libc++.so`）。NAPI 模块链接它时，它先于 `libc++_shared.so` 进入查找范围，被测库的 typeinfo 引用被它抢走，libc++ 按地址比较 typeinfo，所有 `catch (const std::exception&)` 失配（表现为 `std::terminate` 与 “exception not derived from std::exception”）。修复：不再链接，改为 `dlopen(RTLD_LOCAL)` 后 `dlsym` 取 `OH_Ability_StartNativeChildProcess`。
2. **`debug_hap` 域对 memfd 的 `fstat` 返回 `EACCES`**：经 SCM_RIGHTS 收到的 memfd 上 `fstatfs`（TMPFS_MAGIC）、`F_GET_SEALS`（0x6）、`mmap` 都可用，只有 `fstat` 被拒，selfdev `MapSegment` 原先依赖 `fstat` 取类型与大小，订阅全部以 “rejected by publisher: corrupted” 失败。修复（`src/platform.cc`）：先查封印（要求 `F_SEAL_SHRINK`）；`fstat` 以 `EACCES` 失败时，大小取 `lseek(SEEK_END)`（已封 SHRINK，不会再缩小），类型由“TMPFS 且有封印”确定；其他 `fstat` 错误仍为 `kSystem`。x86 回归：PL-14、RG-43（故障注入 `fault::fstat_denied`）。订阅者的拒绝日志补上了原因。
3. **子进程 cwd 为 `/`**：runner 创建 `./cfg` 失败；子进程改为 `chdir` 到日志所在目录。
4. **子进程崩溃时父进程等满超时**：改为 pidfd（见上）。
5. **runner 的 `DYN_ABI` 在库形式下 exe 列为 unresolved**：runner 库以 `RTLD_LOCAL` 打开，`RTLD_DEFAULT` 看不到它的依赖；库构建改用自身句柄（`dlopen(RTLD_NOLOAD)`）作为查找范围（`RunnerScope()`），可执行文件构建不变。

### 7.1b loan 路径通道 `shm_loan_v2`、`shm_loaned_ctx`、`shm_loaned_pod`

| 通道 | 对标 | 发布路径 | 订阅 |

| `shm_loan_v2` | `iox_loan_v2` | 公开 API：Setup 中 `SenderRef::RegisterLoanedPodTopic()` 注册 POD 主题，每拍 `LoanedSample<T>::Borrow` → 原位填充 → `Publish`（kPodOnly，无序列化、无拷贝）。不强转驱动，不链接 iceoryx/shm_ext | `iox_loan_v2` 的订阅模块源码（`LoanedSubscriber<T>::AttachBytes`） |

注：`iox_loaned_pod` 原样例在 `Run()`（即 `Engine::Start` 之后）才调用 `CreateRawPodPublisher` / `RegisterRawPodSubscriber`，而 iceoryx 驱动只在 Init 态接受 POD 注册，报 “CreateRawPodPublisher failed”，无法运行。本仓库已修复：发布/订阅模块新增 `RegisterWithDriver()`，由 `main()` 在 `Initialize()` 注入驱动后、`Start()` 之前调用（模块 `Setup` 运行于驱动注入之前，不能放在 Setup）；注册失败则进程返回 -1，`Run()` 检测未注册时报错。`shm_loaned_pod` 沿用同一时机。

### 7.2 对标基准脚本

`selfdev/shm/scripts/bench_transport_lanes.sh [latency] [cpu]`：iox_send / shm_send /（可选）dds_send_shm 多轮交替运行（`LANES` 可换成 loan 通道，见 §7.1b），输出各通道各负载中位数（`$OUT_DIR/latency.md`、`cpu.csv`）。属于基准：无样本的运行标记为 NO SAMPLES（如默认 RouDi 池下 iox_send 4MB），脚本恒返回 0，不按数值判失败；需要判定的 CI 使用严格矩阵（§7.1）。中断（Ctrl-C/kill）时 cpu 阶段复原配置并停止通道进程；被 `kill -9` 残留的备份在下次运行时先行复原。参数见脚本头。结果与分析见 `对标基准.md`。
