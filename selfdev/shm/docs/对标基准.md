# ibmw_shm 对标基准（阶段 3）

> 日期 2026-10-29；机器 Intel i7-14700（28 线程），Linux 5.15，Release 构建（GCC 11）。
> 对标对象：iceoryx（IBMW 现用，RouDi 守护进程）、Fast DDS 2.6.11（系统包，SHM 传输）。
> 结论先行：**同等 Send 路径下，自研 shm 与 iceoryx 的 p50/p90 持平（≤64KB 的 p99 也持平；256KB~1MB 的尾部百分位噪声大，见 §2），CPU 持平或略低，且无需 RouDi、无 4MB 上限；Fast DDS 小负载 p50 约为两者的 2 倍，≥1MB 尾时延劣化两个数量级。**

## 1. 测试方法

三条通道都运行 `src/samples/cpp/transport_benchmark` 的两进程基准（发布进程 + 订阅进程），负载为 `CompressedImage` 风格的 CDR 消息，100 Hz，订阅侧按发布时间戳统计端到端时延（含序列化、拷贝、通知、反序列化与回调）。

| 通道 | 传输 | 发布路径 | 守护进程 |
|---|---|---|---|
| `iox_send` | iceoryx（`libibmw_iceoryx_transport.so`） | `ibmw::transport::Send()`：CDR → 堆缓冲 → memcpy 进 SHM 块 | RouDi |
| `shm_send` | 自研 shm（`libibmw_shm_transport.so`，`driver_name: iceoryx`） | 同上（**同一份模块源码**，只换 yaml 中的扩展项） | 无 |
| `dds_send_shm` | Fast DDS SHM 传输 | 同上（DDS 驱动） | 无 |

- `shm_send` 即“原位替换”迁移路径：发布/订阅模块直接编译 `iox_send` 的源码，配置只把扩展项换成 `libibmw_shm_transport.so` 并设 `driver_name: iceoryx`，`messaging` 段（驱动类型 `iceoryx`、`enable_drivers`、路由规则）不变。可执行文件与扩展均不链接 iceoryx（`ldd` 核对）。
- 每个负载 3 轮、每轮 20 s（约 1950 个样本；Fast DDS E2E 为固定 1800 条），轮间交替通道顺序，表中为 3 轮中位数。
- CPU：稳态窗口（启动后 6 s 起 20 s）内所有通道进程（含 RouDi）的 utime+stime 之和，单位为单核百分比。

复现：

```bash
# 构建：IBMW_BUILD_EXAMPLES=ON IBMW_BUILD_BENCHMARKS=ON ICEORYX/SHM 扩展 ON（DDS 通道另需 IBMW_BUILD_DDS_EXTENSION=ON）
BUILD_DIR=<bench build> [DDS_BUILD_DIR=<dds build>] [PIN_CPUS=2-7] selfdev/shm/scripts/bench_transport_lanes.sh
# 脚本只报告 NO SAMPLES、恒返回 0（基准不判失败）。或只跑严格矩阵（含 shm_send，无样本即失败）：
BUILD_DIR=<bench build> PAYLOAD_BYTES=4096 src/samples/cpp/transport_benchmark/validate_transport_bench_matrix.sh iox_send shm_send
```

排查过程：驱动 Send 路径与 iceoryx 驱动一致（按记忆的尺寸提示一次 loan、一次序列化）。当时认为发布者“100 Hz 下复用刚归还的热块”，这一判断**不准确**：空闲表虽为 LIFO，但 `Loan` 只在空闲表为空时才回收归还环，单在途流因此在两块之间交替（工作集翻倍）。该问题在 loan 路径对标中定位并修复，见 §5.3；修复后 Send 路径大负载复测见 §5.4。

## 3. CPU（100 Hz 稳态，单核 %，3 轮中位数）

| 负载 | iox_send（发布+订阅+RouDi） | shm_send（发布+订阅） |
|---|---|---|
| 4KB | 0.70 | **0.55** |
| 1MB | 6.09 | **5.80** |

- 1MB 时 CPU 主要花在两条通道共有的 CDR 序列化 + memcpy + 反序列化上；4KB 时自研少一个 RouDi 进程，控制面开销更低。
- 空闲开销见测试文档 §4（核心库基准：1 pub + 1 sub + listener 空闲 2 s CPU 0.009 ms，无周期唤醒）。

## 4. 结论与说明

1. **iceoryx 原位替换**：现有 iceoryx 部署只改 yaml 的扩展项即可切换，业务代码与 `messaging` 配置不变；时延、CPU 与 iceoryx 持平，省去 RouDi 守护进程及其配置（内存池需按最大消息预先配置，否则大消息失败）。
2. **相对 Fast DDS**：同一 Send 路径下，≤256KB 时 p50 约为 Fast DDS 的 0.45~0.6 倍；≥1MB 时 Fast DDS p90 以上进入 10~90 ms（分片/流控），自研 4MB 的 p99.9 为 1.4 ms、max 2.3 ms。
3. §2/§3 为 **Send（拷贝进 SHM）** 路径，与现网 iox_send 对齐；真正零拷贝的 loan 路径（POD loan、ctx-meta loan）见 §5。
4. `dds_loaned` 的 E2E 脚本只做功能校验（`csv_path: ""`），不产出时延，未纳入对比。
5. 数值为本机单次会话测量，未设实时优先级；不同机器只比较相对关系。原始 CSV：`/oee_work/flx/aitest/bench-results/`（runs/ 为非绑核三通道，pinned/ 为绑核复核，cpu.csv）。
6. 干扰说明（2026-11-05 补记）：本文各表均在与他人共用的本机上测得，测量时没有逐轮干扰判定；本文没有 OHOS 设备表格。设备上的数值（测试文档 §6.5、§6.6、§6.9 等）同样只在开跑前避让外来基准，未逐轮判定干扰。此后的设备性能数按测试文档 §6.18 的方法测量（只用干净轮）；以上历史数值保持原样，未重新解释。

## 5. loan 路径（零拷贝）对标

### 5.1 通道与方法

| 通道 | 对标 | 发布路径 | 订阅模块 |
|---|---|---|---|
| `shm_loan_v2` | `iox_loan_v2` | 公开 API：Setup 中 `RegisterLoanedPodTopic`，每拍 `LoanedSample<T>::Borrow` → 原位填充 → `Publish`（kPodOnly，无序列化、无拷贝） | 同一份 `iox_loan_v2` 订阅源码 |
| `shm_loaned_ctx` | `iox_loaned_ctx` | `ShmCtxMetaTypedPublisher<T>`（EXT-29）：loan → CDR 直接序列化进块 → 发布 | `iox_send` 订阅源码（标准 `OnMessage<T>`） |
| `shm_loaned_pod` | `iox_loaned_pod` | 扩展专用 API：`CreateShmRawPodPublisher`（EXT-30）→ `Borrow(N)` → 原位写 `BenchPodHeader` + 填充 → `Publish`（kPodOnly） | 驱动原始 POD 回调（`RegisterPodSubscriber`），与 iox 侧逻辑相同 |

两条发布端每拍工作相同（`iox_loaned_ctx` 与 `shm_loaned_ctx` 都堆分配消息、填充、发布）。时延戳均在回调入口、任何校验之前取得，故时延可比；**但 ctx 通道 CPU 不可直接对比**：`shm_loaned_ctx` 复用的 `iox_send` 订阅回调逐字节校验整个负载（1MB 即扫 1MB），`iox_loaned_ctx` 的订阅回调不校验负载。

时延含发布端负载填充：`FillBenchPlainPayload` 先打 send 时间戳再 memset 填充区，因此 POD loan 在 4MB 的 ~260µs 主要是填充本身（参考：核心库基准单次 4MB memcpy 173µs，测试文档 §4）。

`iox_loaned_pod` 原样例在 `Engine::Start` 之后才注册 POD 发布者/订阅者，iceoryx 驱动报 “CreateRawPodPublisher failed” 而无法运行；本仓库已修复注册时机（`main()` 在 Initialize 与 Start 之间调用 `RegisterWithDriver()`，见测试文档 §7.1b），对标结果见 §5.5。`FillBenchPod` 同样先打时间戳再填充，与 loan_v2 通道可比。

### 5.3 本轮发现并修复的问题：大负载热块复用

修复前首轮（`bench-results/loan`）shm_loan_v2 在 4MB 的 p50 稳定高约 8%（3 轮 256/261/268 对 iox 245/234/242）。逐进程采样（/proc 计数，未存档）：缺页 0 次/s、发布端 CPU 相同，排除缺页与额外拷贝。定位：发布者空闲表为 LIFO，但 `PublisherImpl::Loan` 只在空闲表为空时才回收订阅者的归还环（`Publish` 时回收）。单在途流中刚归还的块要到下一次 `Publish` 才回到空闲表，`Loan` 因而总拿到另一块——两块交替，4MB 工作集变为 8MB，填充写入的块总是冷的。

修复（`selfdev/shm/src/publisher.cc`）：`Loan` 先无条件回收归还环再取块（无归还时每连接一次原子读）。新增 PS-17 `ReleasedChunkIsReusedFirst`：loan→发布→取走→释放循环 100 次每次拿到同一块，订阅者持有中的块不被借出；撤回修复后该用例失败。修复后 4MB 差距进入噪声（见上表，p50 +2%，区间重叠）。

该问题同样影响 Send 路径（Send 内部也先 loan）。§2 的 Send 结果是修复前测得；修复后复测（`bench-results/send_post`，3 轮，绑核）：

| 负载 | iox_send p50 / p99 | shm_send p50 / p99 |
|---|---|---|
| 256KB | 87.6 / 875.0 | 83.3 / 143.0 |
| 1MB | 221.5 / 678.4 | 220.7 / 416.2 |
| 4MB | 失败（RouDi 池） | 999.3 / 1834.2 |

256KB/1MB 仍持平。4MB 本次为 917/1033/999（§2 修复前为 871.9），iox 在该负载无对照样本，无法区分是本次运行的整机噪声（§5.2）还是路径变化；4MB Send 的主成本是两端各一次 4MB 序列化/反序列化拷贝，修复只影响块选择，不增加工作量。

### 5.6 结论

1. 公开 POD loan API（`RegisterLoanedPodTopic` + `LoanedSample<T>`）在自研 shm 上无需改业务代码即可工作，时延与 iceoryx 持平、CPU 略低（少一个 RouDi）。
2. ctx-meta loan 通过 `TransportDriver` 基类虚函数即可使用（无需强转驱动类型），≤1MB 与 iceoryx 持平；4MB 在 iceoryx 默认配置下不可用，自研无需预配置内存池。
3. 对标中发现并修复了大负载下的块交替问题，Send 与 loan 路径同时受益。
4. 扩展专用的原始 POD 接口（`CreateShmRawPodPublisher` / `RegisterPodSubscriber`，对应 iceoryx 的 `CreateRawPodPublisher` / `RegisterRawPodSubscriber`）1KB~4MB p50 时延与 iceoryx 持平、4MB 合并 8 轮 p99 持平（小负载 p99 各有高低，受噪声影响），CPU 中位数更低（§5.5）；`iox_loaned_pod` 样例的注册时机缺陷已在本仓库修复。
