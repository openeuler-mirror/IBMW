# ibmw_shm 对标基准（阶段 3）

> 日期 2026-10-29；机器 Intel i7-14700（28 线程），Linux 5.15，Release 构建（GCC 11）。
> 对标对象：iceoryx（IBMW 现用，RouDi 守护进程）、Fast DDS 2.6.11（系统包，SHM 传输）。
> 结论先行：**同等 Send 路径下，自研 shm 与 iceoryx 的 p50/p90 持平（≤64KB 的 p99 也持平；256KB~1MB 的尾部百分位噪声大，见 §2），CPU 持平或略低，且无需 RouDi、无 4MB 上限；Fast DDS 小负载 p50 约为两者的 2 倍，≥1MB 尾时延劣化两个数量级。**

## 1. 测试方法

三条通道都运行 `src/samples/cpp/transport_benchmark` 的两进程基准（发布进程 + 订阅进程），负载为 `CompressedImage` 风格的 CDR 消息，100 Hz，订阅侧按发布时间戳统计端到端时延（含序列化、拷贝、通知、反序列化与回调）。

| 通道 | 传输 | 发布路径 | 守护进程 |
|---|---|---|---|
| `iox_send` | iceoryx（`libibmw_iceoryx_transport.so`） | `ibmw::transport::Send()`：CDR → 堆缓冲 → memcpy 进 SHM 块 | RouDi |
| `shm_send` | 自研 shm（`libibmw_shm_transport.so`，`driver_name: iceoryx`） | 同上（**同一份模块源码**，只换 yaml 中的扩展项） | 无 |
| `dds_send_shm` | Fast DDS SHM 传输 | 同上（DDS 驱动） | 无 |

- `shm_send` 即“原位替换”迁移路径：发布/订阅模块直接编译 `iox_send` 的源码，配置只把扩展项换成 `libibmw_shm_transport.so` 并设 `driver_name: iceoryx`，`messaging` 段（驱动类型 `iceoryx`、`enable_drivers`、路由规则）不变。可执行文件与扩展均不链接 iceoryx（`ldd` 核对）。
- 每个负载 3 轮、每轮 20 s（约 1950 个样本；Fast DDS E2E 为固定 1800 条），轮间交替通道顺序，表中为 3 轮中位数。
- CPU：稳态窗口（启动后 6 s 起 20 s）内所有通道进程（含 RouDi）的 utime+stime 之和，单位为单核百分比。

复现：

```bash
# 构建：IBMW_BUILD_EXAMPLES=ON IBMW_BUILD_BENCHMARKS=ON ICEORYX/SHM 扩展 ON（DDS 通道另需 IBMW_BUILD_DDS_EXTENSION=ON）
BUILD_DIR=<bench build> [DDS_BUILD_DIR=<dds build>] [PIN_CPUS=2-7] selfdev/shm/scripts/bench_transport_lanes.sh
# 脚本只报告 NO SAMPLES、恒返回 0（基准不判失败）。或只跑严格矩阵（含 shm_send，无样本即失败）：
BUILD_DIR=<bench build> PAYLOAD_BYTES=4096 src/samples/cpp/transport_benchmark/validate_transport_bench_matrix.sh iox_send shm_send
```

**256KB/1MB 复核（绑核 2-7，5 轮交替）**：未绑核时 shm_send 在 256KB/1MB 的 p50 略高（+16µs），但各轮区间重叠（iox 1MB p50 210~246，shm 223~250）。绑核复测后差异消失：

| 负载 | 通道 | p50 | p90 | p99 | p99.9 |
|---|---|---|---|---|---|
| 256KB | iox_send | 88.2 | 127.0 | 161.7 | 199.8 |
| 256KB | **shm_send** | 87.3 | 116.5 | 158.2 | 855.9 |
| 1MB | iox_send | 210.0 | 263.6 | 421.3 | 1135.1 |
| 1MB | **shm_send** | 208.4 | 253.3 | 403.2 | 928.2 |

尾部百分位：256KB/1MB 的 p99.9/max 每轮只有约 2 个样本落在 0.1% 以内，受单次调度抖动支配。非绑核时 1MB shm_send p99/p99.9（512/917）差于 iox_send（395/498）；绑核复测 1MB 反过来（403/928 对 421/1135），而 256KB 绑核时 shm_send p99.9 856 对 200。两条通道都出现过单轮离群，样本量不足以判定尾部孰优，结论只针对 p50~p99 的稳定部分；需要尾部对比时应在绑核 + 实时优先级下延长运行（如 `DURATION_SEC=300`）。

排查过程：确认发布者块空闲表为 LIFO，且 `Publish` 在投递前回收归还环（`publisher.cc` DrainAllLocked），100 Hz 下复用的是刚归还的热块；驱动 Send 路径与 iceoryx 驱动一致（按记忆的尺寸提示一次 loan、一次序列化）。差异属调度噪声，不是结构性开销。

## 3. CPU（100 Hz 稳态，单核 %，3 轮中位数）

| 负载 | iox_send（发布+订阅+RouDi） | shm_send（发布+订阅） |
|---|---|---|
| 4KB | 0.70 | **0.55** |
| 1MB | 6.09 | **5.80** |

- 1MB 时 CPU 主要花在两条通道共有的 CDR 序列化 + memcpy + 反序列化上；4KB 时自研少一个 RouDi 进程，控制面开销更低。
- 空闲开销见测试文档 §4（核心库基准：1 pub + 1 sub + listener 空闲 2 s CPU 0.009 ms，无周期唤醒）。

## 4. 结论与说明

1. **iceoryx 原位替换**：现有 iceoryx 部署只改 yaml 的扩展项即可切换，业务代码与 `messaging` 配置不变；时延、CPU 与 iceoryx 持平，省去 RouDi 守护进程及其配置（内存池需按最大消息预先配置，否则大消息失败）。
2. **相对 Fast DDS**：同一 Send 路径下，≤256KB 时 p50 约为 Fast DDS 的 0.45~0.6 倍；≥1MB 时 Fast DDS p90 以上进入 10~90 ms（分片/流控），自研 4MB 的 p99.9 为 1.4 ms、max 2.3 ms。
3. 本报告只覆盖 **Send（拷贝进 SHM）** 路径，与现网 iox_send 对齐。真正零拷贝的 loan 路径（`iox_loaned_ctx/pod` 对应物）需要基准模块改为面向 shm 驱动的 loan API（现样例强转为 `IceoryxTransportDriver`），列为后续工作；核心库层面的零拷贝时延见测试文档 §4（与负载大小无关）。
4. `dds_loaned` 的 E2E 脚本只做功能校验（`csv_path: ""`），不产出时延，未纳入对比。
5. 数值为本机单次会话测量，未设实时优先级；不同机器只比较相对关系。原始 CSV：`/oee_work/flx/aitest/bench-results/`（runs/ 为非绑核三通道，pinned/ 为绑核复核，cpu.csv）。
