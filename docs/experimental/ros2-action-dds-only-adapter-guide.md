# ROS2 Action DDS-only Adapter Guide

This guide is for developers who want to run a ROS2 Action server through IBMW's DDS-only action path:

```cpp
ibmw::action::ActionServerNode<Traits, Hook>
```

The goal is low-code hand adaptation today, with a shape that can later be generated by `ibmw-gen`.

Status: experimental. The API is usable for checked-in samples, but it is not yet a public `.action` generator or product-level cross-RMW claim.

## What this path gives you

The server process owns FastDDS endpoints directly and does not link the ROS2 runtime stack:

- no `rcl`
- no `rclcpp`
- no `rclcpp_action`
- no `rcl_action`
- no `rmw`

A native ROS2 client or server can still be used as a validation peer.

## Mental model

A DDS-only action server is split into four layers:

| Layer | File/class | Responsibility |
|------|------------|----------------|
| Generic node | `ibmw::action::ActionServerNode<Traits, Hook>` | FastDDS participant, ROS2 action service endpoints, feedback/status publishers, worker threads |
| Generic runtime | `ibmw::action::ServerRuntime<Hook, ...>` | Goal lifecycle, cancellation, result retention, pending `GetResult` fan-out |
| Wire traits | `ibmw::action::ActionTraits<MyAction>` | ROS2 action request/response/message type aliases and goal-id accessors |
| Action adapter | `ibmw::action::ActionServerBinding<Traits, Hook>` | Converts action-specific Goal/Result/Feedback fields to and from plain Hook payloads |

`Hook` is the only business-logic layer. Keep ROS2 wire message structs out of it.

## Naming rules

Use the real ROS2 action type name in action-specific files. For example, `Fibonacci` is not a generic IBMW name; it is the official ROS2 sample action type:

```text
example_interfaces/action/Fibonacci
```

Use generic names only for reusable IBMW layers:

- `ActionServerNode`
- `ServerRuntime`
- `ActionTraits`
- `ActionServerBinding`

If a demo reuses an existing ROS2 wire type for a different Hook, name it honestly. For example, `countdown_fibonacci_wire_action_server.cpp` means: countdown business logic using the official Fibonacci action message shape as the wire container.

## Files to write for a new ROS2 Action type

For `my_pkg::action::DoThing`, create:

1. `do_thing_action_traits.h`
2. `do_thing_action_hook.h`
3. `do_thing_action_server_binding.h`
4. `do_thing_action_server.cpp`

Then add a CMake target that links the action's generated ROS2 type targets and the IBMW action support libraries.

## Step 1: define `ActionTraits`

`ActionTraits` is types-only. It names the ROS2 wire structs and gives the generic runtime a uniform way to read goal IDs.

```cpp
#include <my_pkg/action/do_thing.hpp>
#include <unique_identifier_msgs/msg/uuid.hpp>

#include "cpp/action/action_traits.h"

namespace ibmw::action {

template <>
struct ActionTraits<my_pkg::action::DoThing> {
  using Action = my_pkg::action::DoThing;
  using Goal = Action::Goal;
  using Result = Action::Result;
  using Feedback = Action::Feedback;
  using SendGoalRequest = Action::Impl::SendGoalService::Request;
  using SendGoalResponse = Action::Impl::SendGoalService::Response;
  using GetResultRequest = Action::Impl::GetResultService::Request;
  using GetResultResponse = Action::Impl::GetResultService::Response;
  using FeedbackMessage = Action::Impl::FeedbackMessage;
  using GoalId = unique_identifier_msgs::msg::UUID;

  static constexpr const char* kActionTypeName = "my_pkg/action/DoThing";

  static const GoalId& goal_id_of(const SendGoalRequest& request) { return request.goal_id; }
  static const GoalId& goal_id_of(const GetResultRequest& request) { return request.goal_id; }
  static const GoalId& feedback_goal_id(const FeedbackMessage& message) { return message.goal_id; }
};

}  // namespace ibmw::action
```

Checklist:

- Include the generated ROS2 action header.
- Use `Action::Impl::*Service::*` aliases; do not invent custom service structs.
- Keep this specialization in `namespace ibmw::action`.
- Do not put validation or execution logic here.

## Step 2: define the Hook

The Hook owns business logic only. It uses plain C++ payload types.

```cpp
#include <cstdint>

#include "cpp/action/server_runtime.h"

struct DoThingHook {
  using GoalInput = int32_t;
  using FeedbackPayload = int32_t;
  using ResultPayload = bool;

  struct ExecState {
    int32_t target = 0;
    int32_t progress = 0;
  };

  static bool ValidateGoal(const GoalInput& goal) { return goal > 0; }

  static ExecState InitState(const GoalInput& goal) {
    return ExecState{.target = goal, .progress = 0};
  }

  static ibmw::action::TickOutcome Tick(ExecState& state) {
    ++state.progress;
    return state.progress >= state.target ? ibmw::action::TickOutcome::kSucceeded
                                          : ibmw::action::TickOutcome::kContinue;
  }

  static FeedbackPayload BuildFeedback(const ExecState& state) { return state.progress; }
  static ResultPayload BuildResult(const ExecState&) { return true; }
};
```

Hook contract:

| Member | Required behavior |
|--------|-------------------|
| `GoalInput` | Plain value extracted from `SendGoalRequest` by the binding |
| `FeedbackPayload` | Plain value converted to `FeedbackMessage` by the binding |
| `ResultPayload` | Plain value converted to `GetResultResponse` by the binding |
| `ValidateGoal` | Return `false` to reject invalid goals before execution starts |
| `InitState` | Build per-goal execution state from the accepted goal input |
| `Tick` | Advance one execution step; return `kContinue`, `kSucceeded`, `kCanceled`, or `kAborted` |
| `BuildFeedback` | Snapshot current feedback payload from execution state |
| `BuildResult` | Snapshot final result payload from execution state |

Do not mutate state on the same `Tick` call that returns a terminal status unless the final state is exactly what `BuildResult` should publish.

## Step 3: define `ActionServerBinding`

`ActionServerBinding` is the only layer that knows action-specific field names.

```cpp
#include "cpp/action/action_server_binding.h"
#include "do_thing_action_hook.h"
#include "do_thing_action_traits.h"

namespace ibmw::action {

template <>
struct ActionServerBinding<ActionTraits<my_pkg::action::DoThing>, DoThingHook> {
  using Traits = ActionTraits<my_pkg::action::DoThing>;
  using Hook = DoThingHook;

  static Hook::GoalInput GoalInputOf(const Traits::SendGoalRequest& request) {
    return request.goal.target;
  }

  static Traits::GetResultResponse ToGetResultResponse(int8_t status,
                                                       const Hook::ResultPayload& result) {
    Traits::GetResultResponse response;
    response.status = status;
    response.result.ok = result;
    return response;
  }

  static Traits::FeedbackMessage ToFeedbackMessage(const Traits::GoalId& goal_id,
                                                   const Hook::FeedbackPayload& feedback) {
    Traits::FeedbackMessage message;
    message.goal_id = goal_id;
    message.feedback.progress = feedback;
    return message;
  }
};

template <>
inline constexpr bool kActionServerBindingSpecialized<ActionTraits<my_pkg::action::DoThing>,
                                                      DoThingHook> = true;

}  // namespace ibmw::action
```

Binding checklist:

- `GoalInputOf` reads from `request.goal`.
- `ToGetResultResponse` always sets `response.status`.
- `ToGetResultResponse` writes only `response.result.*` fields.
- `ToFeedbackMessage` always sets `message.goal_id`.
- `ToFeedbackMessage` writes only `message.feedback.*` fields.
- Set `kActionServerBindingSpecialized<...> = true`.

If the bool specialization is missing, `ActionServerNode` fails at compile time with a static assertion.

## Step 4: write the server entrypoint

```cpp
#include <atomic>
#include <chrono>
#include <csignal>
#include <thread>

#include "cpp/action/action_server_node.h"
#include "do_thing_action_server_binding.h"

using Traits = ibmw::action::ActionTraits<my_pkg::action::DoThing>;
using Hook = DoThingHook;

std::atomic_bool stop{false};

void HandleSignal(int) { stop.store(true); }

int main() {
  std::signal(SIGINT, HandleSignal);
  std::signal(SIGTERM, HandleSignal);

  ibmw::action::ActionServerNode<Traits, Hook> server("/do_thing");
  if (!server.Start(0)) {
    return 1;
  }
  while (!stop.load()) {
    std::this_thread::sleep_for(std::chrono::milliseconds(200));
  }
  return 0;
}
```

The constructor argument is the ROS2 action name, not the action type name. For example:

- action type: `my_pkg/action/DoThing`
- action name: `/do_thing`

## Step 5: add CMake wiring

A server target needs:

- `ibmw::api::cpp`
- `ibmw::core::engine`
- `ibmw::extensions::dds_types`
- `ibmw::internal::ros2_action_dds`
- generated ROS2 action/message headers
- FastRTPS C++ typesupport libraries for the action and shared action message packages

Use the Fibonacci sample CMake as the reference:

```text
src/samples/cpp/ros2_action_fibonacci_dds_server/CMakeLists.txt
```

Build the checked-in targets with:

```bash
cmake --build build --target ibmw_action_dds_generic_fibonacci_server -j$(nproc)
cmake --build build --target ibmw_action_dds_countdown_fibonacci_wire_server -j$(nproc)
cmake --build build --target ibmw_action_dds_generic_gripper_command_server -j$(nproc)
```

## Step 6: validate

For compile/link validation, build the server target and check that the binary does not link ROS2 runtime libraries:

```bash
ldd build/ibmw_action_dds_generic_fibonacci_server | grep -E 'librcl(|cpp|cpp_action)|librmw|librcl_action'
```

Expected result: no matches.

For the checked-in Fibonacci interop validation, build:

```bash
cmake --build build --target ibmw_action_dds_generic_fibonacci_server ibmw_fibonacci_action_ros2_client -j$(nproc)
```

Then run the sample harness from the repository root:

```bash
SERVER_TARGET_NAME=ibmw_action_dds_generic_fibonacci_server \
SERVER_BIN=build/ibmw_action_dds_generic_fibonacci_server \
CLIENT_BIN=build/ibmw_fibonacci_action_ros2_client \
bash src/samples/cpp/ros2_action_fibonacci_dds_server/validate_ros2_client_to_ibmw_server.sh success
```

For the checked-in GripperCommand interop validation, build:

```bash
cmake --build build --target ibmw_action_dds_generic_gripper_command_server ibmw_gripper_command_action_ros2_client -j$(nproc)
```

Then run:

```bash
VALIDATION_ACTION=gripper_command \
bash src/samples/cpp/ros2_action_fibonacci_dds_server/validate_ros2_client_to_ibmw_server.sh success
```


## Adapting a second Hook to the same wire type

If you only want to prove a different business policy while reusing an existing ROS2 action type, write a new Hook and a second binding specialization for the same `ActionTraits` but a different Hook.

Checked-in example:

```text
src/samples/cpp/ros2_action_fibonacci_common/countdown_action_server_binding.h
src/samples/cpp/ros2_action_fibonacci_dds_server/ros2_server/countdown_fibonacci_wire_action_server.cpp
```

This demo maps:

| ROS2 wire field | Countdown meaning |
|-----------------|-------------------|
| `request.goal.order` | starting count |
| `feedback.sequence` | countdown progress snapshots |
| `result.sequence` | final countdown sequence |

This is useful for compile coverage and adapter structure validation. It is not a semantic replacement for defining a real second `.action` type.

## Generator-facing `.action` runtime bridge design

This section records the intended `ibmw-gen import` direction for arbitrary ROS2 `.action` interfaces. It is a design boundary, not an implementation claim. Today, `.action` import remains metadata / compile-skeleton oriented unless a checked-in hand adapter exists for the specific action type.

### Import modes

`ibmw-gen import` should keep the same two-lane policy used for `.msg` and `.srv`:

| Situation | Mode | Generator responsibility |
|-----------|------|--------------------------|
| Installed ROS2 package already provides the action | `reference_existing` | scan `<ros2-prefix>/share/<pkg>/action`, report `available_types`, generate IBMW adapter skeletons that include existing rosidl headers |
| No installed package exists | `generate_package` | copy or emit `.action` files into a rosidl package skeleton, then generate the same IBMW adapter skeletons against that package |

`reference_existing` remains preferred when a package/type already exists. It avoids copying interface definitions and keeps exact rosidl type ownership with the upstream package.

### Generated artifact shape

For `pkg/action/Foo`, a future generator slice should produce these files before any higher-level app wrapper is claimed:

```text
include/pkg/ibmw_interface_types.hpp
include/pkg/ibmw_action_traits.hpp
include/pkg/ibmw_action_binding_skeleton.hpp
include/pkg/ibmw_action_runtime.hpp
pkg_reference_existing_action_runtime.ibmw.yaml   # reference_existing
pkg_imported_action_runtime.ibmw.yaml             # generate_package
ibmw_interface_report.json
```

The report should explicitly distinguish:

- `available_types`: all discovered `msg/*`, `srv/*`, and `action/*` selectors in the package;
- `selected_types`: the user-requested action selectors;
- `action_runtime.generated`: whether a runnable server/client adapter was generated;
- `action_runtime.status`: one of `metadata_only`, `compile_skeleton`, `server_runtime`, `client_runtime`, or `bidirectional_runtime`;
- `boundary.runtime_dependency_policy`: `rcl_free_ibmw_runtime`.

### Layer split

The generated action bridge must preserve the same split as the hand adapters:

1. **Type aliases** — include the rosidl action header and expose `Goal`, `Result`, `Feedback`, `SendGoal`, `GetResult`, `CancelGoal`, feedback-message, and status-message aliases.
2. **FastDDS type support wrappers** — bind only to rosidl-generated FastRTPS C++ type-support artifacts. Do not introduce IBMW envelope types for ROS2 action endpoints.
3. **ActionTraits specialization** — generated, types-only, no business logic.
4. **Binding skeleton** — generated user regions that map action-specific fields into plain Hook payloads.
5. **Runtime adapter** — generic `ActionServerNode` / future client node wiring, goal registry, cancel/result/status behavior, and DDS endpoint lifecycle.
6. **App/module YAML** — generated only once the runtime adapter is at least compile-valid for the selected action.

The Hook remains user-owned business logic. Generated code must not require users to manipulate ROS2 wire structs inside Hook state.

If action bindings need editable regions, they should reuse the existing public user-region marker grammar unless a later design explicitly adds action-specific marker categories and tests them. Action drivers should also integrate through the same typed-slot ABI used by other IBMW drivers, rather than introducing a separate package-entry mechanism.

### Host/target boundary

Generator discovery is host-side only:

- use `<ros2-prefix>/share/<pkg>/action` scanning for installed packages;
- do not require `ament_index_python`, `ros2` CLI, `rclpy`, `rclcpp`, or `rclcpp_action` for import;
- record `host_tools_prefix` and `target_runtime_prefix` separately in the JSON report;
- keep native ROS2 clients/servers as external live harness peers only.

Target builds must link generated IBMW action binaries only against IBMW, DDS/FastDDS/FastCDR, and rosidl-generated type-support libraries. `rcl`, `rclcpp`, `rclpy`, `rcl_action`, `rclcpp_action`, `rmw`, `ament_index_cpp`, and `ament_index_python` remain forbidden runtime dependencies.

### Runtime acceptance gates

A future generated `.action` runtime is not accepted until all of these pass for at least one installed `reference_existing` action and one source-mode `generate_package` action:

1. IBMW DDS-only action server is discovered by a native ROS2 Humble action client.
2. Native ROS2 Humble action server is discovered by the future IBMW DDS-only action client.
3. SendGoal accepted and rejected paths preserve UUID and timestamp semantics.
4. Feedback messages are received and correlated by goal UUID.
5. GetResult returns terminal status and result payload, including late result retrieval.
6. CancelGoal follows ROS2 cancel semantics and status transitions.
7. Status publication uses ROS2-compatible type, topic, QoS, and goal-state values.
8. Route B target artifact audit passes for cross-built target binaries with at least one AArch64 ELF artifact and no forbidden host-prefix leak. In this document, Route B means the OHOS/AArch64 cross-build lane using target DDS/rosidl prefixes and the repo checker that writes `route_b_target_artifact_audit.json`.

Until those gates exist and pass, docs and reports should say `metadata_only` or `compile_skeleton`; they must not claim generic `.action` runtime support.

## Common mistakes

- Putting ROS2 wire structs into the Hook.
- Forgetting `kActionServerBindingSpecialized<...> = true`.
- Mapping result fields into feedback fields, or the reverse.
- Forgetting to set `response.status` in `ToGetResultResponse`.
- Forgetting to copy `goal_id` in `ToFeedbackMessage`.
- Hand-writing lifecycle status transitions in the Hook instead of returning `TickOutcome`.
- Linking the DDS-only server against `rcl`, `rclcpp`, `rclcpp_action`, `rcl_action`, or `rmw`.
- Treating a reused wire type demo as proof of a new ROS2 action type.

## Current limitations

- This is low-code hand adaptation, not automatic `ibmw-gen` output.
- Checked-in validation covers `example_interfaces/action/Fibonacci` and installed `control_msgs/action/GripperCommand` on ROS2 Humble with FastRTPS C++ typesupport.
- New arbitrary `.action` packages still require generated ROS2 FastRTPS C++ typesupport and handwritten/generated FastDDS trait wrappers.
- The validation harness now has Fibonacci and GripperCommand modes; additional action semantics still need matching validation clients or a more generic action-client checker.
