# IBMW 核心竞争力构建路线（2026-2030，讨论稿）

## 1. 竞争力定位

核心竞争力不是功能清单，而是相对 ROS2 等主流中间件，在目标场景中能够持续兑现、且不容易被替代的优势。

ROS2 的优势是成熟的接口、工具、软件包和跨行业生态。IBMW 不应与其割裂，也不应只做一个“轻量版 ROS2”；IBMW 的路线是：**在明确的类型、QoS、发现和服务/Action 边界内复用 ROS2 接口资产及 DDS 互通能力，对不依赖 rcl/rclcpp 运行时语义的资产实现渐进迁移，并逐步建立面向具身智能的高性能通信、自适应调度和跨异构系统确定性。**

由此形成三层递进的竞争力：

1. **2026，0→1：生态兼容、轻量完整、基础性能领先。** 既能承接 ROS2 生态，又不支付额外运行时和性能成本，并在大载荷关键链路形成可感知的加速优势。
2. **2027，1→10：高性能、自适应调优、软硬协同确定性。** 在选定硬件上形成显著差异化能力。
3. **2028-2030，10→100：跨硬件泛化、规模化生态和成熟平台能力。** 把单点优势变成可复制、可持续的平台壁垒。

三阶段不是三条独立产品线，而是同一架构的演进：2026 建好接口、运行时、生成与验证底座；2027 把 Timing Budget、Priority 和数据生命周期贯通调度、通信、NPU 与 RTOS；2028-2030 再通过经过验证的版本化契约和适配层推广到更多算力平台与软件生态。

## 3. 第一阶段：2026 年，构建“兼容不降速、轻量且高效”的基础竞争力（0→1）

### 3.1 要形成的竞争优势

对标 ROS2，2026 年 IBMW 不是先做一个“功能可用”的替代品，而是形成一套具有明确推广价值的基础竞争力：**ROS2 资产迁得过来，DDS 兼容链路不交性能税，目标设备部署更轻，大载荷关键链路还能显著提速。**

- **生态可复用**：支持 ROS2 `msg/srv/action` 资产导入，并在经过验证的类型、QoS、发现和服务/Action 场景下实现 DDS/ROS2 互通，使符合边界的设备、工具和软件节点能够渐进接入。
- **兼容路径不降速**：在同硬件、同 QoS 和同负载下，IBMW DDS 兼容模式守住 ROS2/Fast DDS 基线的完成率、P99、CPU 和 PSS，使迁移不是以性能退化换取框架替换。
- **运行时更轻**：业务进程不依赖 rcl/rclcpp，在资源受限设备、OpenHarmony 和交叉编译场景中减少运行时依赖与部署复杂度，并以更小部署包和更短构建链降低产品化成本。
- **能力完整**：具备开发、通信、执行、配置、日志、监控、录制回放和生命周期管理等中间件基础能力，不因“轻量”退化成只能收发消息的通信库。
- **关键数据链路更快**：对点云、图像等大载荷提供 SHM/Loaned Message 基础快通道，在语义等价前提下，使 P99 降至 DDS 兼容路径的 `1/3` 以下、最大稳定吞吐达到 `2` 倍以上，形成可被业务直接感知的收益。
- **开发交付更简单**：通过统一配置、`ibmw-gen`、交叉编译 SDK 和标准验证链路，降低从 ROS2 资产到目标设备应用的迁移成本。

这形成 2026 年的产品定位：**对 ROS2 生态兼容而不被其运行时绑定，常规 DDS 路径不降速，大数据路径有加速，功能完整但部署更轻，开发交付更简单。** 这不是单点 benchmark 优化，而是“迁移成本、运行资源、基础性能、关键链路性能”四项同时成立的综合优势。所有结论仍需在同硬件、同场景、同 QoS 条件下形成可复核数据，不能只靠架构推断。

### 3.2 统一对标基线

2026 年不做无限范围的 ROS2 兼容承诺，竞争力结论统一限定在以下基线内：

- **目标设备与操作系统**：x86 Host Ubuntu、OHOS Xiaoyi CPro、openEuler Embedded AArch64，分别覆盖开发验证、具身设备端和嵌入式 Linux 场景。
- **ROS2 与 RMW**：ROS2 主流 LTS 版本 Humble；DDS/RMW 只选择 Fast DDS（`rmw_fastrtps_cpp`）作为统一兼容与性能对标基线，其他 ROS2 发行版和 RMW 不进入 2026 年正式承诺。
- **软件包范围**：主流 SLAM 软件包及其传感器依赖，覆盖激光雷达、相机、IMU 等典型输入链路；具体软件包和版本形成冻结清单。
- **接口资产范围**：常用 ROS2 `msg/srv/action` 类型不少于 `500` 个，按类型依赖闭包、生成结果、编译结果和 DDS 互通结果建立兼容清单；Action 语义仍按实验性边界单独验收。

这组基线既用于验证“ROS2 生态能够迁移”，也用于比较运行包体积、构建时长、PSS/CPU、DDS 兼容路径和 SHM/零拷贝收益，避免不同平台、RMW 或软件包口径混用。

### 3.3 建议验收目标

以下数字是 2026 年竞争力建设的**建议门槛**，需在完成首轮 A/B/C 基线采集后评审固化，不代表当前已经达到。A 为 ROS2/RMW 原始路径，B 为 IBMW DDS 兼容路径，C 为 IBMW SHM/零拷贝路径。

| 竞争力维度 | 2026 建议验收目标 | 统一口径 |
|---|---|---|
| DDS 兼容迁移性能 | 固定负载下，B 相对 A 的完成率不下降，P99 点估计不高于 A；初始统计等价区间为 `±5%`，只用于处理测量不确定性，不能解释为允许性能下降；超过 `+10%` 自动阻断并归因。P99.9 先报告，待样本与置信区间规则固化后再进入门禁 | 同硬件、同进程边界、同 QoS、同 payload、同 offered load、同等优化级别；容量搜索另行比较最大稳定吞吐 |
| 内存与 CPU | 固定负载下，B 的稳态 PSS、CPU 点估计不高于 A；置信区间上界允许最多 `5%` 测量不确定性；长稳测试无持续内存增长；RSS 只作诊断 | 统计业务及必要中间件进程，排除工具自身资源 |
| 部署体积 | 在选定软件包与功能等价清单下，IBMW 目标板运行包相比 ROS2 等价运行包至少缩小 `50%`，挑战目标 `70%` | 冻结软件包/版本、目标架构、Release/Strip/LTO、必备功能测试和运行依赖闭包；同时报告压缩发布包与解压安装体积，不计业务模型/数据 |
| 构建效率 | 干净环境一条命令构建，无人工补丁；同等并行度下 clean build 时长至少降低 `30%`，增量构建至少降低 `50%` | 固定功能输入、工具链、并行度、缓存状态和产物范围；分别报告 cold-cache、warm-cache 和 incremental，不要求不同实现使用相同源码 |
| 构建易用性 | 从接口导入到目标板可运行包形成单一工作流；至少 `20` 个独立干净环境中首次任务完成率不低于 `95%`；失败能够自动定位到依赖、生成、编译、链接、部署或运行阶段 | 记录命令数、人工补丁数、完成时长、失败阶段和诊断正确率；以新环境、新开发者和 CI 三类任务复跑验收 |
| SHM/零拷贝基本能力 | 支持 Loaned Message、跨进程 SHM 和所有权回收；`zero_copy_used/fallback` 必须可观测，fallback 必须显式报告而非静默复制；进程异常后默认 `5 s` 内完成 loan/SHM 回收，重复故障注入后无残留增长 | 先覆盖 plain/POD 和选定大载荷类型；回收超时可由场景契约覆盖，能力边界显式输出 |
| 关键场景性能 | 对 `256 KB-1 MB` 点云/图像类同机跨进程场景，固定负载下达到 `C.P99 <= B.P99 / 3`，挑战 `C.P99 <= B.P99 / 5`，且 CPU 至少降低 `30%`；容量搜索中达到 `C.max_stable_throughput >= 2 * B.max_stable_throughput` | A/B/C 中 C 与 B 保持业务语义、可靠性、顺序性、进程边界和资源核算等价；不等价时只展示带能力标签的 Pareto 结果 |

这里的“不下降”不是只看平均时延，而是同时守住正确性、完成率、P99、PSS、CPU 和过载行为；P99.9 作为趋势指标持续报告，暂不参与通过/失败判定。正式比较至少包含 `5` 个有效 A/B/C 配对 block，P99 每轮至少包含 `10,000` 个有效样本，并报告运行间离散度与置信区间。SHM/零拷贝的倍数收益只针对满足条件的大载荷关键场景，不外推到所有消息类型。

### 3.4 支撑措施

- 补齐并稳定 Module 生命周期、Parameter、Logger、Watchdog、Executor、Transport 等基础契约。
- 完善 Record/Playback，覆盖录制、切卷、筛选、时序回放、异常恢复、并发和长稳，使其成为问题复现、算法回归和性能分析的基础设施。
- 完善 `ibmw-gen` 对 ROS2 接口的导入、类型转换、工程生成和交叉构建支持；Action 在完成双向互通与生成闭环前保持实验性边界。
- 建立 install SDK、交叉编译、打包部署、CTest/pytest、DDS/ROS2 live acceptance 和真机 smoke 的统一流水线。
- 依据[《ROS 2 与 IBMW 性能采集及可观测性设计》](performance-observability-design.zh.md)持续建设统一的 `mw-perf-collect`。当前 `doctor/run/validate/report`、单机采集及严格 artifact 校验已实现，`compare` 与独立 A/B/C runner 仍是边界明确的原型；完整自动矩阵与正式统计平台属于后续建设。
- 建立 A（ROS2/RMW）、B（IBMW DDS 兼容）、C（IBMW 新 Transport）三组对照，统一采集完成率、RTT/P99/P99.9、吞吐、CPU、PSS、网络和构建/包体数据；正式结论只使用满足相同场景契约的外部公共指标。
- 在 IBMW 内部补充默认关闭、按需启用的 counters 与路径诊断，覆盖发布、序列化、队列、Driver、接收和回调阶段；内部指标用于归因，不能替代公共指标参与胜负比较。
- 对观测工具自身做扰动校准：Off 模式性能影响不可测或低于噪声；Counters/P1 模式初始预算为主业务 CPU 变化不超过 `2` 个百分点、吞吐损失不超过 `3%`、P99 增幅不超过 `5%`，最终门槛由目标平台 pilot run 固化，并在每份报告中记录实际观测开销。

### 3.5 阶段完成标志

典型 ROS2 消息、服务及选定软件包能够依据明确边界迁移到 IBMW；开发者可从干净环境完成生成、构建、部署、运行、录制回放和故障定位；`mw-perf-collect` 能够一键复跑 A/B/C 并生成可审计报告；选定基准集同时通过 DDS 兼容不降速、PSS/CPU 不增加、部署包至少缩小 50%、clean build 至少提速 30%，以及大载荷 SHM 路径 P99 降至 DDS 兼容路径 `1/3` 以下等门槛。**达到这一状态，IBMW 才不只是“另一个可用中间件”，而是具备明确迁移动机和推广说服力的更优基础底座，完成从 0 到 1。**

## 4. 第二阶段：2027 年，构建“面向具身负载的自适应确定性”性能竞争力（1→10）

### 4.1 要形成的竞争优势

2027 年的重点平台边界明确为：**有限绑定昇腾 310 系列，采用 RC 模式，以 310P RC 为主验证平台；应用生态以 LeRobot 为主要入口，IB-Robot 在 LeRobot 基础上增强中间件、异构调度和实时控制能力。** 这一选择用于把 1→10 的性能竞争力做深，不代表长期绑定单一硬件。

具身智能不是单一消息链路，而是多模型、多传感器、多算力和多控制周期同时运行的动态系统。相机、激光雷达、IMU、力觉等传感器具有不同频率、载荷和突发特征；感知、定位、预测、VLM/VLA 推理、规划和控制又会形成不同优先级的模型流水线；CPU、NPU、GPU、ISP、DSP 和 RTOS 控制核之间还存在资源竞争与数据搬运。

在 ROS2 通用 API 和常见 RMW 默认配置下，这些通信 QoS、线程执行、异构推理和 RTOS 控制通常不是由一套统一的时限预算语义贯通。IBMW 在 2027 年要形成的差异化优势，不是针对某个孤立 benchmark 做优化，而是针对以下具身负载族，提供可调度、可观测、可退化的系统能力：

- **多模型并发场景**：在感知、跟踪、定位、预测、VLM/VLA 和规划模型同时运行时，关键控制与低优先级后台模型不互相无界挤占；模型负载变化后可以重新配置调度策略。
- **多元传感器融合场景**：在相机/点云/IMU/力觉等不同速率、不同 payload 的数据同时进入系统时，保持时间戳、优先级、顺序和融合窗口语义，避免高频小消息或大图像流把控制数据淹没。
- **多算力协同场景**：让 CPU、NPU、GPU/ISP、DSP 和 RTOS 控制核按照任务特征协同执行，减少不必要的跨域复制和等待，使数据路径与算力选择共同服从端到端时限预算。
- **动态资源竞争场景**：在模型切换、传感器突发、后台建图或日志录制等负载变化下，系统能够识别预算消耗，执行限流、降级、迁移或回退，而不是只在平均负载下保持性能。

围绕这些场景，IBMW 要形成的差异化优势是：

- **优先级调度**：业务优先级、Deadline 和 Timing Budget 不停留在消息元数据，而能影响 Executor、队列、传输和任务执行顺序。
- **异构软调度与自适应调优**：结合选定 NPU/SoC 的运行时能力，根据负载、尾延迟和任务优先级选择经验证的调度策略组合；对抢占、核隔离和 NPU 队列策略明确平台依赖及不可动态调整的边界。
- **通信与计算协同优化**：DDS、SHM/Loaned Message 与 NPU 数据路径共享调度上下文，减少复制、反序列化和错误唤醒造成的尾抖动。
- **软硬协同确定性**：通过 DSF 与 RTOS 结合，建立 Linux/NPU 侧软实时任务与关节控制等 RTOS 硬实时任务之间可测量、可诊断的预算关联，形成从感知、推理到控制的闭环；跨系统关联不直接等同于统一硬实时保证。

这一阶段正式绑定范围限定为昇腾 310 系列 RC 模式，并以 310P RC 为主验证平台；其他 NPU/SoC 仅用于验证抽象可扩展性，不进入 2027 年产品承诺。竞争力不在“支持硬件多”，而是在这一平台边界内把上述具身负载族做深：在同一硬件、同一传感器/模型负载、同一 QoS 和同等优化级别下，相对 ROS2/RMW 基线形成可复核的 P99/P99.9、按时完成率、资源占用和过载退化优势，并证明这些优势能够从单一链路迁移到多模型、多传感器和多算力协同场景。

### 4.2 支撑措施

- 实现 Scheduler Plugin ABI 和策略运行时，支持策略替换、在线比较、故障隔离与安全回退。
- 贯通 Executor、DDS、SHM 和异构任务的 Priority、Deadline、Timing Budget 传递及降级检测。
- 对接重点 NPU 的任务队列、事件唤醒、内存/DMA 和性能计数器，形成基于运行状态的调优闭环。
- 先完成 IPC/SHM 的 Loaned Message 所有权与异常回收，再验证 NPU-DMA、IOMMU 和缓存一致性。
- 围绕 LeRobot 与 IB-Robot 增强栈建立具身负载场景矩阵，至少覆盖：多模型并发、多传感器融合、310P NPU 推理与 CPU 后处理、多算力资源竞争，以及感知—推理—控制闭环；每类场景同时定义正常、突发、降级和恢复工况。
- 选择一种 DSF（Deterministic Scheduling Framework，确定性调度框架）形态完成 Linux+RTOS 端到端验证。两种候选形态分别是同 SoC 单核常驻 RTOS，以及主 CPU+板载 MCU；先以其中一种承载上述场景矩阵中的关键控制链路，验证长稳、过载、资源降级和故障恢复。

### 4.3 阶段完成标志

在明确的目标硬件和负载下，调度策略无需修改框架核心即可替换和回滚；优先级与时限预算可在已验证的通信、CPU/NPU 和 RTOS 集成边界内追踪，并能区分各边界的预算消耗和违约原因；场景矩阵中的关键场景达到预设控制周期和按时完成率，并对突发、降级、恢复工况给出可解释结果；在动态资源竞争以及感知—推理—RTOS 控制闭环中，相对同等优化的 ROS2/RMW 基线和硬件固定队列，仍形成可复核的尾延迟、自适应、资源利用和可控退化优势。此时 IBMW 完成从 1 到 10。

## 5. 第三阶段：2028-2030 年，构建“跨平台可验证确定性”的生态竞争力（10→100）

### 5.1 要形成的竞争优势

长期竞争力不是继续为单一硬件堆优化，而是把 2027 年在昇腾 310P RC 上验证的能力抽象并复制出去。业务范围面向具身机器人全面展开，不只覆盖 SLAM 和 VLA，还包括 WBC（Whole-Body Control，全身控制）以及需要在机器人侧运行的业界大小模型，并同时支持机器人本地端侧与云边、边端协同场景：

- **异构算力可替换**：通过版本化的调度插件、设备能力描述和适配 ABI，让不同 NPU/GPU/AI 加速器接入同一调度与观测体系。
- **确定性语义可跨平台复用**：Timing Budget、Priority、数据生命周期和故障语义跨 Linux、OpenHarmony、RTOS、SoC+MCU 等形态保持接口和测量方法一致，同时允许性能上限和确定性等级因平台而异。
- **生态软件获得完整加速能力**：SLAM、VLA、WBC、感知、规划控制及具身大小模型的软件包适配，从“改成 DDS 兼容、能够收发消息”，升级为可直接使用 IBMW 的零拷贝、高性能通信、优先级调度、异构协同和确定性诊断。
- **端侧与云边协同统一承载**：端侧关键闭环使用本地高性能通信与确定性调度，云边或边端链路使用跨主机 Transport 和资源编排，在同一应用模型下区分实时边界、数据路径和降级策略。
- **成熟可用且可规模复制**：形成长期兼容、认证、诊断、发布和升级体系，使机器人产品不必为每种硬件重复建设中间件底座。

届时 IBMW 的壁垒不只是代码，而是**跨平台稳定契约、硬件适配方法、软件包迁移规范、确定性测试认证以及长期积累的真实负载与失效数据**。

### 5.2 支撑措施

- 对经过验证的 Scheduler Plugin、设备能力描述、跨后端 Timing/Priority、零拷贝生命周期和 DSF 语义，在明确版本、架构和兼容范围内逐步冻结 v1 API/ABI；内部实现不承诺 ABI 稳定。
- 从重点 NPU 扩展到多类异构算力，形成设备能力发现、策略选择、性能模型和统一可观测接口。
- 补齐 DSF 双形态，并在多 SoC、多 RTOS/MCU 上完成一致性、长稳、过载、时钟漂移与故障验证。
- 建立面向第三方传输、调度器、硬件和软件包的 SDK、一致性测试套件与准入机制。
- 推动感知、SLAM、规划控制、VLA、WBC 及具身大小模型由“协议兼容移植”升级为“IBMW 原生高性能适配”，形成覆盖机器人端侧和云边/边端协同的可复用软件包与行业场景矩阵。

### 5.3 阶段完成标志

核心契约在明确兼容范围内跨多个硬件平台和版本保持兼容；第三方无需修改框架核心即可接入新的异构算力或调度策略；代表性软件包能够同时获得通信和调度加速；DSF 两种形态具备产品级验证；关键场景形成基于明确平台、负载和测试条件的确定性等级、测量方法和诊断门禁。IBMW 从特定平台上的优势实现，成长为具身智能系统可规模采用的中间件平台。

## 6. 竞争力演进与架构关系

三阶段竞争力由同一条技术链逐步展开：

> ROS2 生态兼容与轻量完整运行时 → 可观测的通信/执行基线 → 统一 Priority/Timing Budget → NPU 自适应软调度 → RTOS/DSF 确定性闭环 → 跨硬件 ABI 与生态原生适配。

需要保持四个边界：

- 2026 的核心是“生态兼容、功能完整、部署轻量、基础性能领先”：DDS 迁移不降速，大载荷链路有明确加速，不能只写成易用性补齐。
- 2027 的核心是“在特定硬件上做深性能与确定性”，不追求同时覆盖所有平台。
- 2028-2030 的核心是“把硬件绑定的优势泛化并规模复制”，不是简单增加适配数量。
- 推文中的 Ascend 310P 软调度、三级零拷贝、DSF 双形态和 10 ms VLA 时间轴是 PoC 或架构输入；只有进入 IBMW 版本、通过明确平台与负载下的端到端验证后，才能转化为产品竞争力结论。

## 7. 已明确的阶段边界

1. **2026 对标边界与竞争力门槛**：x86 Host Ubuntu、OHOS Xiaoyi CPro、openEuler Embedded AArch64；ROS2 Humble + Fast DDS；主流 SLAM 与传感器依赖；不少于 500 个常用 ROS2 接口类型。在此范围内实现 DDS 兼容不降速、PSS/CPU 不增加、部署包至少缩小 50%、clean build 至少提速 30%，大载荷 SHM 路径 P99 降至 DDS 兼容路径的 `1/3` 以下。
2. **2027 深化边界**：有限绑定昇腾 310 系列 RC 模式，以 310P RC 为主；围绕 LeRobot 和 IB-Robot 增强栈构建多模型、多传感器、多算力、动态资源竞争与 RTOS 控制场景矩阵。
3. **2028-2030 泛化边界**：面向 SLAM、VLA、WBC、感知、规划控制及具身大小模型的全面业务，覆盖机器人本地端侧以及云边、边端协同，把高性能通信和调度能力推广到多类异构算力平台。
