# IBMW SDK Delivery Manual

Version: v0.1

Use this manual when delivering IBMW as a reusable SDK install prefix for
customer builds. Do not require customers to rebuild the IBMW source tree when a
validated per-architecture SDK is available.

## Capability profiles

The intended long-term SDK model is "build once, develop many components". That
means one per-architecture development SDK should expose enough capabilities for
multiple teams and modules: local/minimal, JSON, DDS, ROS2-compatible DDS,
generated `.msg` / `.srv` / `.action`, and install-prefix consumers.

A full-flag SDK can contain multiple capabilities, but consumer applications
must link and deploy only the components they use. Validate component resolution
and the final dependency closure for each delivered profile rather than assuming
one prefix is appropriate for every target.

Interim policy:

- Build IBMW / the SDK **per required capability set** instead of publishing one
  universal full-capability SDK.
- For OHOS, each capability set must be cross-compiled with the matching target
  profile, sysroot, and target dependency prefixes; a host SDK never substitutes
  for an OHOS SDK.
- Treat trimmed SDKs as intentional scoped profiles, not as general development
  SDKs.
- Before delivery, audit the resulting app's actual target ELF dependency
  closure, not just the SDK prefix contents.

## Architecture rule

- Host tools run on the build host/container: CMake, Python `ibmw_gen.py`,
  `fastddsgen`, JRE, Jinja/PyYAML, and IBMW helper scripts.
- Generator helper scripts may ship in `<sdk>/bin`, but they still execute on
  the host/container and require host Python/JRE/tool availability.
- Cross SDKs must be generated by cross-compiling IBMW for the target. A host
  SDK is not an OHOS SDK.
- Target SDK provides target-architecture headers, libraries, CMake exports,
  helper CMake modules, and target third-party dependencies.
- Customer projects consume the SDK with `find_package(ibmw)` and a toolchain
  file. Generated C++ is text; only compilation/linking is target-architecture.
- Current caveat: `find_package(ibmw)` + exported targets are still being
  hardened for strict componentized dependency isolation. Verify that a consumer
  only resolves/links the components it requested.

## Boundary truth

- Prefer install-tree SDK consumption. ROS2-enabled build-tree consumption is not
  the customer contract.
- Route B/OHOS builds may run outside or inside a build container. In both modes,
  the target artifact audit is the authority.
- Prefer FastDDS/Fast-CDR from the target ROS2 prefix when Route B uses ROS2
  dependencies. Do not silently use bundled/newer fallbacks.
- Board runtime validation is separate from cross compile/link/audit.

## Required evidence

- SDK prefix path and architecture.
- `lib/cmake/ibmw/ibmw-config.cmake` exists.
- External consumer configure/build passes with `CMAKE_PREFIX_PATH=<sdk>`.
- For cross SDKs, target ELF arch audit passes.
- For OHOS SDK runtime claims, `/data/<case>` target run log shows startup PASS.
- For Route B/OHOS, `scripts/check_ohos_route_b_link_boundary.sh` or the Route B
  compile wrapper produced a PASS `route_b_target_artifact_audit.json`.
- FastDDS/Fast-CDR provider is recorded.

## Profile claim ladder

Pick the SDK profile from `reference/profiles.md` before claiming capability.
Every claim must be tagged as `(host runtime)`, `(OHOS board runtime)`, or
`(cross audit only)`.

Host SDK evidence template `(host runtime)`:

```text
SDK prefix: <host-sdk-prefix>
Consumer: <external-consumer-source>
Build dir: ${TMPDIR:-/tmp}/ibmw-sdk-consumer-build
Result: <configure/build/runtime result>
```

This seed proves host install-prefix SDK consumption and host app runtime. It
does not replace Route B target audit or OHOS board runtime validation.

OHOS minimal SDK evidence template `(OHOS board runtime, hello-world only)`:

```text
SDK build: ${TMPDIR:-/tmp}/ibmw-ohos-sdk-build
SDK prefix: <ohos-sdk-install-prefix>
Consumer build: ${TMPDIR:-/tmp}/ibmw-ohos-consumer-build
Target path: /data/<case>
Result: <cross install, consumer build, and target run result>
Evidence: <evidence-dir>/ohos_run.log
Audit: <evidence-dir>/consumer_target_artifact_audit.json
```

Such evidence can prove a minimal OHOS target SDK was consumed and run for the
recorded case. It does not prove DDS/ROS2 runtime.

DDS/ROS2 Route B/OHOS SDK `(cross audit only)`:

- Requires a target DDS/ROS2-capable SDK profile, not the minimal OHOS SDK.
- Required evidence is a current-tree `route_b_target_artifact_audit.json` PASS.
- DDS/ROS2 OHOS board runtime is **NOT VERIFIED** until a `/data/<case>` target
  run log proves a DDS/ROS2 case on the board.
